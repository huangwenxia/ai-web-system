#预览机制设计

##目标
为个人前端资产体系补齐“预览层”设计，让候选组件与候选页面在进入真实项目前，具备可视化验证、状态验证、布局验证与 approval 前审查能力。

这份文档覆盖两层预览：

1. 独立 workbench预览
2.真实项目集成预览

---

## 为什么必须有预览层
如果只有“生成 →评审 → 同步”，而没有专门预览层，会出现几个问题：

-只能看代码，很难高效判断视觉与交互质量
- 候选组件是否值得晋升，缺少直观验证入口
- 页面结构是否合理，只能靠想象或直接进项目验证
-过早把候选资产放进真实项目，容易污染正式代码

因此，预览层不是附属能力，而是这套知识库机制的中间基础设施。

---

## 总体原则
###1. 候选资产先在知识库预览
所有候选组件、候选页面，先在 `ai-web-system` 内完成第一轮预览。

###2. 成熟后再做真实项目集成预览
只有通过知识库内初步审查的资产，才进入真实项目壳下做第二轮集成验证。

###3. preview只做验证，不直接替代正式业务页面
preview 路由只是额外入口，不是 DEV 下的正式页面替身。

###4. approval之前不允许正式覆盖
无论预览做了多少轮，在 approval 前都只能停留在：
-知识库候选区
-项目 preview区

不能进入正式业务目录。

## 第一层：独立 workbench预览
### 推荐承载位置
- `E:\work\ai-web-system\apps\ai-front-workbench`

当前该目录还没有实际代码，因此建议它作为后续独立预览壳的正式承载位置。

当前已补上第一版最小骨架，可用于后续继续扩展候选组件独立预览。

###依赖原则
独立 workbench 的“独立”，仅表示目录与入口独立，不表示依赖生态独立。

建议原则：
- workbench依赖优先对齐当前真实项目
- 优先复用 `project-mamba` 已有的 Vue、Vue Router、workspace UI / utils / hooks 包
- 已使用 Tailwind 的项目，workbench也应优先保持 Tailwind组织方式一致
- 不为了预览便利额外引入项目中不存在的新 UI / 样式基础设施

一句话：

**独立的是预览壳，不是运行生态。**

###目标
独立 workbench主要用于：
- 单组件预览
- 单页面草稿预览
- props切换
- mock 数据切换
-空态 / loading / 错误态验证
-视觉结构初审

### 为什么先独立预览
优点：
- 不污染真实项目
- 建设成本低
-适合快速试错
-适合知识库资产沉淀
-适合把候选组件当作长期资产经营

### 独立 workbench阶段推荐流程
1. AI生成候选组件 / 页面到 `assets`
2. 创建 manifest
3. 在 `ai-front-workbench` 注册预览入口
4. 做视觉 /结构 / 状态初审
5.通过后再考虑进入真实项目集成预览

## 第二层：真实项目集成预览
###目标
这一步不是为了替换正式页面，而是为了验证：
- 候选资产在真实项目整体布局下是否协调
- 是否适配真实项目的依赖、主题、样式基线和上下文
- 是否与真实项目的布局容器、滚动区域、头部、侧栏节奏一致

### 核心原则
####只新增入口，不替换正式入口
集成预览必须遵守：

- 正式业务路由继续走正式自动生成路由
- preview只额外挂在 `/__preview__/...`
- preview不能在 DEV 下偷偷替换正式业务页面

这条规则是防止混淆的关键。

#### preview 区是“项目内验证壳”，不是正式业务目录
候选资产即便进入 `project-mamba`，也只是进入集中式 preview区，而不是业务组件目录。

---

## 集成预览目录策略
### 推荐目录名
- `__preview__`

不推荐：
- `.preview`：在 Windows / IDE 环境中不够友好
- 分散在各业务目录下的 `preview` / `demo` / `__demo__`

### 推荐目录位置
在某个宿主 app 内统一保留一个 preview区，例如：

```text
apps/common/src/__preview__/
```

或者你后续选中的任意宿主 app。

### 为什么只要一个集中 preview区
因为 preview只是同步前验证层，不是正式业务层。

所以：
- 不要每个组件层级都加预留目录
- 不要把 preview散落在不同业务模块中
-只要一个集中式 preview容器

---

## 自动路由项目如何适配
你的项目前端路由是自动生成的，这并不妨碍 preview接入。

### 最推荐方式：路由生成后追加 previewRoutes
思路：
- 正式业务路由照常自动生成
- 在 router 创建阶段，仅本地 DEV 环境额外挂入 previewRoutes

关键点：
- previewRoutes只是新增 `/__preview__/...`入口
-不会替代正式路由
- 正式业务路径仍然指向正式页面

### 错误做法
不要在 DEV 下把正式路由改去指向 preview文件。

错误示例（原则上禁止）：

```ts
if (DEV) {
 OrderDetailPage = PreviewOrderDetailPage
}
```

因为这样会导致：
- DEV 环境看到的不是真正正式实现
- approval 前后容易混淆
- preview与正式实现边界消失

正确做法应该始终是：

**preview作为额外入口并存，而不是替换正式入口。**

---

## approval机制
### approval 前
允许：
-进入知识库 workbench预览
-进入真实项目 preview区预览
- 做兼容性检查、视觉审查、成熟度评审

不允许：
- 写入正式组件目录
- 替换正式业务页面
-修改正式业务引用链

### approval 后
才允许：
- 正式同步到项目目标目录
- 正式业务页面开始使用新实现
- 更新 manifest 的同步状态

因此，preview 的存在并不代表已经进入正式实现链。

##个人试验阶段的特殊策略
因为你当前不是给整个团队使用，而是个人探索阶段，所以建议采用更轻量的策略。

### 推荐策略
- `project-mamba` 中使用 `__preview__`
- 整个 `__preview__`目录直接 git ignore
- `ai-web-system`继续保留正式文档、manifest、脚本与资产记录

也就是说：
- `ai-web-system` 是长期资产中心
- `project-mamba/__preview__` 是你本地真实项目集成预览沙盒

这是当前阶段最符合你目标的方案。

---

## 当前推荐的完整链路
1. AI生成候选组件 / 页面到 `ai-web-system/assets`
2. 创建 manifest
3.先在 `ai-front-workbench` 做独立预览
4.通过后，同步到 `project-mamba` 的 `__preview__` 做集成预览
5.你人工做 approval
6. approval 后，才允许同步到正式目录

---

## 一句话结论
预览机制要分两层：

- **独立 workbench**：先做知识库候选资产预览
- **真实项目 `__preview__`**：再做同步前集成验证

并始终遵守：

**preview只新增入口，不替代正式入口；approval 前只能预览，不能正式覆盖。**
