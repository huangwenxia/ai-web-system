#组件成熟度评审规范

##目标
定义一个组件从“任务草稿”成长为“知识库正式资产”再到“真实项目可同步组件”的判断门槛。

## 为什么需要这份规范
如果没有成熟度评审，AI 每次生成的组件都会混在一起，最后出现：

- 页面私有拼装被误当成通用组件
- API 混乱、命名漂移
-视觉质量不稳定
- 同步到项目后难以维护

所以需要一个分级机制，明确什么能保留、什么能复用、什么能进入真实项目。

---

## 推荐分级
### L0 临时草稿
适用特征：
-只为当前任务服务
-结构尚未稳定
- 命名偏业务私有
- 边界未补齐

处理建议：
- 可以保留
- 不进入正式资产层
- 不同步到真实项目公共区域

### L1 可复用候选
适用特征：
- 已有一定抽象价值
- API 初步成型
- 可在相似页面复用
-仍需更多案例验证

处理建议：
- 保留在知识库候选层
- 补文档与使用样例
-继续观察复用情况

### L2 知识库正式组件
适用特征：
- 命名通用
- API 较稳定
-视觉表达达到个人标准
- 已覆盖主要边界状态
- 在多个任务中可稳定复用

处理建议：
-进入知识库正式资产层
-作为 AI 后续生成页面的优先参考

### L3 项目可同步组件
适用特征：
- 满足 L2 的全部要求
- 与 `project-mamba` 工程规范兼容
-依赖完全可落地
-适合放入真实项目目录
- 有明确同步目标与使用场景

处理建议：
-允许同步到真实项目
-需要记录同步信息

---

##评审维度
###1.复用价值
要看它是否服务于一类问题，而不是某一个页面的临时结构。

检查问题：
- 是否可能在多个页面重复出现？
- 是否抽象的是稳定模式，而不是一次性业务字段组合？

###2. API 稳定性
检查问题：
- props / events / slots 是否清晰
- 输入输出职责是否明确
- 是否存在过度耦合页面上下文的问题

###3.视觉质量
检查问题：
- 布局是否稳定
- 信息层次是否清楚
-视觉是否符合你的个人标准
- 空态、加载态、错误态是否协调

###4. 边界完整性
检查问题：
- 缺字段如何处理
- 空数据如何处理
- 加载中如何处理
- 错误态如何处理
- 权限态或禁用态如何处理

###5. 工程兼容性
检查问题：
- 是否使用了 `project-mamba` 中不存在的依赖
- 是否符合项目目录和技术约束
- 是否易于落到真实项目中

###6. 文档与说明完整性
检查问题：
- 是否有组件用途说明
- 是否有输入输出说明
- 是否有适用 / 不适用场景说明

---

## 推荐评审输出格式
每次评审建议至少输出：

1. 当前成熟度等级（L0 / L1 / L2 / L3）
2. 判定理由
3.主要优点
4.主要风险
5. 升级到下一等级还缺什么
6. 是否允许同步到真实项目

---

## 与 Agent 的关系
这份规范非常适合作为以下 Agent 的依据：
-组件入库评审 Agent
- 知识库同步评审 Agent

但注意：
- Agent负责给出评审建议
- 是否最终入库 / 同步，仍建议保留人为确认

---

##结论
成熟度评审的本质，是让你的知识库变成“有治理的资产库”，而不是“AI 输出文件堆积区”。
