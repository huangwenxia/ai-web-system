# 四层关系

## 目标
说明 `ai-web-system` 里最核心的四层结构，以及它们之间的依赖关系。理解这四层之后，整个仓库就不会再像一堆散落目录。

## 先给结论
这套系统可以优先按四层理解：

1. 标准层
2. 入口层
3. 资产层
4. 执行与治理层

这四层不是并列堆放，而是上下协作：
- 标准层定义规则
- 入口层组织模型执行
- 资产层沉淀可复用结果
- 执行与治理层负责落地、评审、同步与回写

---

## 第一层：标准层
标准层回答的是：什么叫做对，什么叫做稳定，什么叫做符合规范。

主要内容包括：
- 视觉标准
- 布局标准
- 数据映射标准
- 组件标准
- 文档标准
- 审查口径

对应目录通常是：
- `standards/`
- `docs/` 中的体系和规范文档

没有这一层，模型就只能靠临场发挥，输出质量无法稳定。

## 第二层：入口层
入口层回答的是：如何把一项任务正确交给模型执行。

主要内容包括：
- `commands/`
- `skills/`
- `agents/`

这一层的职责是把任务翻译成可执行协议，例如：
- 这个任务应该先分析 schema 再推页面
- 这个任务要先审查再决定是否落地代码
- 这个任务输出必须包含边界态和组件映射表

入口层不是知识库本体，而是知识库的调度入口。

## 第三层：资产层
资产层回答的是：哪些结果值得留下来，下一次还能不能复用。

主要内容包括：
- 组件资产
- 页面资产
- 模式资产
- manifest 元数据
- 示例和案例
- 评审记录

对应目录通常是：
- `assets/`
- `examples/`

如果没有资产层，系统每次都只是在“完成任务”，而不是“积累能力”。

## 第四层：执行与治理层
这一层回答的是：怎么把前面三层真正串起来，并保证结果可控。

主要内容包括：
- 工作台应用
- 自动化脚本
- 预览接入
- 项目同步
- 资产晋升
- 评审回写

对应目录通常是：
- `apps/`
- `scripts/`
- `docs/` 中的治理与流程文档

这一层决定系统是否只是静态资料库，还是能真正跑起来。

---

## 四层之间的依赖关系
推荐按下面的顺序理解：

### 标准层 -> 入口层
入口层必须引用标准层。

否则 Skill 和 command 会越来越像个人习惯，而不是稳定协议。

### 标准层 -> 资产层
资产要按标准沉淀。

否则同名组件、页面模式、字段展示方式会越来越乱，最后不可复用。

### 入口层 -> 执行与治理层
工作台和脚本要知道入口层如何组织任务，才能承接执行。

例如：
- 工作台表单要知道输入项有哪些
- 脚本要知道输出物应该落到哪里

### 资产层 -> 执行与治理层
执行与治理层需要消费资产层。

例如：
- 工作台要展示已有组件资产
- 同步脚本要读取 manifest
- 评审流程要依赖已有案例和规则

### 执行与治理层 -> 标准层 / 资产层
这是闭环最关键的一步。

执行过程中发现的新规律、新问题，必须能回写到：
- 标准层
- 资产层
- 示例层

否则系统只会消耗知识，不会增长知识。

---

## 用一个前端任务来理解四层
假设现在有一个“订单详情页”任务：

### 标准层做什么
规定：
- 详情页信息层级如何组织
- 状态如何展示
- 字段如何映射
- 卡片区块如何分组

### 入口层做什么
选择对应的 Skill 或 command：
- 先根据接口推导页面结构
- 再基于组件库落代码
- 最后做视觉和 UX 审查

### 资产层做什么
把这次任务中稳定的部分沉淀下来：
- 订单摘要卡片
- 时间轴区块模式
- 状态标签映射规则
- 页面 manifest 和评审记录

### 执行与治理层做什么
通过工作台和脚本完成：
- 输入整理
- 页面预览
- 资产入库
- 评审回写
- 同步到真实项目

这样一个任务，就能完整穿过四层。

## 为什么这比“多写几个 Skill”更重要
因为 Skill 只覆盖入口层。

如果没有其他三层，结果会是：
- 有很多入口
- 但没有统一标准
- 没有沉淀资产
- 没有治理机制
- 没有同步与回写

所以真正该建设的是“四层协作系统”，不是只扩一层入口。

## 前端视角下的简化理解
如果你不想一次看太多抽象概念，可以先记住：

- 标准层：告诉你怎么做才算好
- 入口层：告诉模型该怎么开始做
- 资产层：把做出来的好结果留下来
- 执行与治理层：把整件事跑通并持续纠偏

这四句话已经足够帮助你理解仓库的大部分目录。

## 当前第一版的现实重点
在第一版里，最优先的不是把四层都做得很重，而是：
- 先把标准层写清楚
- 先把入口层跑顺
- 先把资产层建出最小骨架
- 用工作台和脚本把闭环串起来

这也是为什么当前方案强调：
- 本地优先
- 文件优先
- 轻数据库
- 先工作流、后平台化

## 结论
四层关系不是理论装饰，而是这套系统最核心的理解框架。

只要你始终用“规则从哪来、任务怎么触发、结果沉淀在哪、谁负责落地治理”这四个问题去看项目，整个 `ai-web-system` 就会变得清楚很多。
