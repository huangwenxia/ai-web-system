# 任务类型判断矩阵

## 目标

帮助在接到任务时，先判断它是否属于当前已知工作流，再决定默认主链路和需要叠加的专业能力。

## 当前默认工作流

1. A-既有项目
   - 0. 产品级审查与持续优化
   - 1. 新功能模块页面 / 组件开发
     - 无原型、仅靠后端接口
     - 已有设计稿 / 已确认页面
   - 2. 翻译、术语统一与 i18n
   - 3. bug 修复 / 代码优化
2. B-新系统构建（待定）
3. C-非开发问题 / 纯知识问答

## 双层判断原则

1. 先判任务维度主类型，再决定默认主工作流。
2. 再判当前任务是否需要叠加专业能力，而不是把所有问题都粗暴并进一个入口。
3. “产品级审查与持续优化”首先是默认质量标尺，不等于每次对话都要自动升级成独立审查任务。
4. 如果现有工作流无法低成本覆盖，才进一步判断是否值得新增任务维度 skill。

## 快速矩阵

| 典型任务 | 所属工作流 | 默认主链路 | 需要叠加的专业能力 | 默认产物 | 是否默认回写 |
| --- | --- | --- | --- | --- | --- |
| 无原型、仅靠后端接口的新功能模块 / 页面开发 | A-1 | `existing-project-feature-skill`，内部默认编排 `prototype -> schema-to-ui -> page-design -> frontend-implementer` | 原型推导、字段映射、页面设计、前端实现，必要时叠加 `translate-terms` | 业务梳理、页面骨架、状态边界、设计约束、可落地代码 | 否 |
| 已有设计稿 / 已确认页面的新功能开发 | A-1 | `existing-project-feature-skill`，内部默认编排 `page-design -> frontend-implementer`，其中 `page-design` 以校验和补齐为主 | 页面设计校验、前端实现，必要时叠加 `translate-terms` | 符合项目规范和组件库约束的页面代码 | 否 |
| 英文翻译、术语统一、i18n 改造 | A-2 | `translate-terms-skill`，当前同时兼具任务入口和专业能力 | 文案统一、locale 维护、必要时叠加前端实现 | 术语表、文案替换建议、locale / Vue 修改结果 | 视情况 |
| bug 修复、代码优化、局部体验修正 | A-3 | `existing-project-fix-skill`，内部默认先做上下文追踪，再编排 `frontend-implementer`，必要时叠加结构 / 视觉 / UX 审查 | 上下文追踪、根因修复、必要时叠加结构 / 视觉 / UX 审查 | 修复结果、影响范围、回归风险和验证点 | 否 |

| 新系统构建 | B | 当前无默认链路，必须先确认范围 | 待定 | 待定 | 否 |
| 非开发问题、纯知识问答 | C | 直接问答 | 无 | 直接答复 | 否 |

## 过渡期说明

当前仓库已经落地 `existing-project-feature-skill`、`existing-project-fix-skill`、`product-review-skill` 和 `translate-terms-skill` 作为 A-1 / A-3 / A-0 / A-2 主入口。

因此当前默认策略是：

1. 先按本矩阵识别用户对话属于哪条主工作流。
2. 如果属于 A-1，优先进入 `existing-project-feature-skill`。
3. 如果属于 A-3，优先进入 `existing-project-fix-skill`。
4. 如果属于 A-0，优先进入 `product-review-skill`。
5. 如果属于 A-2，优先进入 `translate-terms-skill`。
6. 其余工作流仍从现有专业 skill 中挑出最合适的执行组合。
7. 等其他任务型主 skill 收敛稳定后，再逐步提升为正式主入口。

## 新任务维度 skill 的判定条件

只有同时满足以下条件，才值得提示用户确认是否新增任务维度 skill：

1. 它明确属于整个产品生产系统的一环。
2. 它能稳定提高效率、质量或交付一致性。
3. 它具有清晰的输入、固定检查点和明确输出。
4. 它会反复出现，而不是一次性特例。
5. 现有工作流和专业 skill 的组合难以低成本覆盖。

如果满足这些条件，必须先向用户说明：

- 它属于哪一环
- 它要解决什么问题
- 没有会怎样
- 为什么值得抽成新的任务维度 skill

在用户确认前，不直接新增 skill，也不新增新文档。

## 回写原则

只有当结论满足这两个条件时，才默认考虑回写：

1. 它已经在多个任务里稳定成立。
2. 它脱离单个任务后仍然有复用价值。

否则就只保留在当前任务结果里。
