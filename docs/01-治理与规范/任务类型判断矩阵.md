# 任务类型判断矩阵

## 目标
帮助你在收到任务时，快速判断：
- 这件事属于哪条工作流
- 是否需要叠加审查流
- 是否需要叠加回写流
- 是否只是一次性实现，不必进入治理动作

这份文档的重点不是抽象分类，而是让你在真实前端开发中能迅速判断“该走哪条流”。

## 先给总原则
默认不要把所有任务都拉进“回写标准”或“沉淀规则”流程。

正确顺序应该是：
1. 先判断任务的主类型
2. 再判断是否需要叠加辅助流程
3. 最后再判断是否值得回写

也就是说：
- 不是所有 bug 都要回写
- 不是所有优化都要沉淀
- 不是所有页面实现都要抽资产

## 一级判断：先分 8 大类
收到任务后，先判断主类型属于哪一类：

1. 纯 bug 修复
2. 代码优化 / 重构
3. 增量需求开发
4. 新页面 / 新模块开发
5. 原型 / 结构推导
6. 审查类任务
7. 文档 / 规则整理
8. 资产治理 / 同步 / workbench 维护

主类型只选一个。

如果任务跨多类，先选“最主要的产出物”。

## 判断矩阵

| 任务场景 | 主工作流 | 常见辅助流 | 默认是否需要回写 | 说明 |
| --- | --- | --- | --- | --- |
| 修复已有 bug | 前端实现工作流 | 按需加页面审查 | 否 | 绝大多数 bug 是局部修复，不需要升级成标准 |
| 优化已有组件代码 | 前端实现工作流 | 页面审查 / UI 审查 | 否 | 只有发现高频结构问题才考虑回写 |
| 重构页面内部结构 | 前端实现工作流 | 页面审查 / UX 审查 | 视情况 | 如果只是局部可维护性提升，通常不回写 |
| 给现有页面加字段 / 加区块 | 前端实现工作流 | schema-to-ui | 否 | 默认是增量实现，不自动进入治理 |
| 新建一个业务页面 | 前端实现工作流 | schema-to-ui / prototype / page-design | 视情况 | 是否回写取决于是否出现可复用模式 |
| 只有接口、没有原型，推页面结构 | 原型 / schema-to-ui 工作流 | page-design | 否 | 先解决页面结构问题，不默认进入标准回写 |
| 根据设计稿落代码 | 前端实现工作流 | UI 审查 | 否 | 默认是实现任务 |
| 审查页面视觉和层级 | 页面审查工作流 | UX 审查 | 否 | 除非发现稳定高频问题 |
| 审查交互路径与认知负担 | UX 审查工作流 | 页面审查 | 否 | 默认是分析任务 |
| 统一文案、术语、状态文案 | translate-terms / 文档工作流 | 页面审查 | 否 | 一般不需要进入规则治理 |
| 补 README / 补文档 | 文档工作流 | 文档规范检查 | 否 | 属于维护类工作 |
| 更新 Skill / Command / Rule | 规则整理工作流 | 治理流 | 是 | 这类任务本身就是规则层工作 |
| 抽组件资产 / page asset / manifest | 资产治理工作流 | 前端实现 / 审查 | 是 | 产物本身就是沉淀 |
| 调整同步脚本 / workbench / 预览机制 | 资产治理 / workbench 工作流 | 文档工作流 | 视情况 | 如果只是实现细节修正，通常不必回写标准 |

## 二级判断：各类型怎么细分

### 1. 纯 bug 修复
典型任务：
- 按钮点了没反应
- 状态显示错了
- 列表不刷新
- 接口成功但 UI 不更新
- 表单校验异常
- 布局错位、样式异常

主工作流：
- 前端实现工作流

可叠加：
- 如果 bug 反映的是结构性问题，再加页面审查流

默认不回写：
- 单点逻辑错误
- 一次性兼容修复
- 某页面的局部样式修复
- 某接口返回处理错误

可能需要回写：
- 同类 bug 在多个页面反复出现
- 暴露出组件 API 设计问题
- 暴露出统一字段映射缺陷
- 暴露出边界态检查规则缺失

一句话判断：
- 修 bug 默认是“修实现”，不是“写规则”。

### 2. 代码优化 / 重构
典型任务：
- 组件职责过载，想拆分
- watch 太多，想整理状态流
- 模板层逻辑太重
- 样式边界混乱
- 页面壳和子组件职责不清

主工作流：
- 前端实现工作流

可叠加：
- 页面审查
- UI 审查
- UX 审查

默认不回写：
- 只优化单个组件的内部写法
- 只为当前页面做结构清理
- 只修可读性、不涉及通用模式

考虑回写：
- 拆分方式可复用
- 某类组件边界问题是高频问题
- 某种响应式写法需要沉淀为禁用模式或推荐模式

一句话判断：
- 优化类任务默认属于实现流，只有形成“稳定经验”时才进治理流。

### 3. 增量需求开发
典型任务：
- 页面加一个筛选项
- 卡片加一个状态展示
- 列表加一列
- 详情页加一个区块
- 现有模块补一个弹窗

主工作流：
- 前端实现工作流

可叠加：
- schema-to-ui
- 页面审查

默认不回写：
- 只服务当前模块的增量改动
- 只新增业务字段展示
- 只改某个项目局部交互

考虑回写：
- 你在增量开发中抽出了通用区块
- 某类展示方式开始重复出现
- 某类状态表达可标准化

### 4. 新页面 / 新模块开发
典型任务：
- 新建列表页
- 新建详情页
- 新建创建 / 编辑页
- 新建某个业务模块

主工作流：
- 如果已有设计稿：前端实现工作流
- 如果没有原型：原型 / schema-to-ui -> 前端实现工作流

可叠加：
- page-design
- page-analysis
- ui-visual-review
- ux-analysis

默认不回写：
- 只是按现有模式复制落地
- 业务强依赖当前场景
- 没有抽出稳定组件和模式

考虑回写：
- 形成新的详情页模板
- 形成新的列表区块模式
- 形成新的字段展示范式
- 形成新的组件复用资产

### 5. 原型 / 结构推导
典型任务：
- 只有接口，没有原型
- 要从需求描述推页面骨架
- 要梳理业务流程和页面结构

主工作流：
- prototype
- schema-to-ui

可叠加：
- page-design
- UX 审查

默认不回写：
- 一次性业务推导
- 强依赖当前产品背景
- 只是某个页面的原型输出

考虑回写：
- 某类业务结构反复出现
- 某类字段组织方式可沉淀
- 某类页面骨架可以形成模板

### 6. 审查类任务
典型任务：
- 看这个页面有没有问题
- 看这个组件写法是否合理
- 看这个交互是否有认知负担
- 看这个视觉层级是否稳

主工作流：
- page-analysis
- ui-visual-review
- ux-analysis

可叠加：
- 前端实现工作流（如果要直接改）

默认不回写：
- 只对当前页面提出修改建议
- 只是一次性 review

考虑回写：
- 问题模式高频重复
- 审查口径已足够稳定
- 可以提炼成标准条目或审查清单

### 7. 文档 / 规则整理
典型任务：
- 整理 README
- 重写 docs 导航
- 补规则说明
- 补命令入口文档
- 调整 Skill / Command / Rule 的边界

主工作流：
- 文档工作流
- 规则整理工作流

是否回写：
- 这类任务本身通常就是“回写动作”

注意：
- 文档维护不等于标准升级
- 规则说明更新不等于标准本体更新

### 8. 资产治理 / 同步 / workbench 维护
典型任务：
- 建 manifest
- 抽候选组件
- 提升资产成熟度
- 同步到项目
- 调整预览接入
- 修改 workbench

主工作流：
- 资产治理工作流
- workbench 工作流

默认不回写：
- 只是修某个同步脚本 bug
- 只是改某个预览页面小问题
- 只是 workbench 局部样式调整

考虑回写：
- 资产目录结构发生稳定变化
- manifest 字段需要长期升级
- 预览映射机制形成稳定规则

## 什么时候明确“不需要回写”
下面这些情况，应明确判断为：

### 1. 一次性项目特例
例如：
- 某个业务字段只在一个项目里存在
- 某个组件写法强依赖项目目录结构
- 某个接口异常处理只适用于当前服务端实现

### 2. 只是修错，不是形成规律
例如：
- 少写了一个判断
- 一个 class 写错了
- 一个 watch 漏清理
- 一个字段映射写反了

### 3. 复用性还没验证
例如：
- 你觉得某种写法不错，但还只用过一次
- 某个区块看起来能复用，但没有经过第二次验证

### 4. 改动粒度太小
例如：
- 文案微调
- 图标替换
- 样式对齐
- 小范围布局修复

### 5. 只是执行层细节
例如：
- 当前任务里为了赶进度做的小实现技巧
- 某段代码的临时兼容写法

一句话标准：
- 没有形成“跨任务稳定收益”，就不要强行回写。

---

## 什么时候值得回写
只有满足以下至少一条，才值得认真考虑回写：

1. 同类问题反复出现至少两次以上
2. 结论可以跨页面 / 跨模块复用
3. 能明显减少下一次同类任务的判断成本
4. 它不是项目偶发特例，而是领域层规律
5. 审查口径已经稳定，可表达为规则或清单

## 推荐的判断顺序
以后你收到任务时，建议按下面顺序问自己：

### Step 1：这件事的主产物是什么？
- 改代码
- 出原型
- 做审查
- 补文档
- 沉淀资产
- 改规则

### Step 2：它最主要属于哪条流？
只选一条主工作流。

### Step 3：需不需要叠加辅助流？
例如：
- 修 bug + UI 审查
- 新页面 + schema-to-ui
- 代码优化 + 页面审查

### Step 4：它是否值得回写？
默认先回答：
- 大概率不需要

只有出现明显稳定规律时，再进入回写判断。

## 典型例子
### 例子 1：修一个表格状态显示 bug
判断：
- 主任务类型：纯 bug 修复
- 主工作流：前端实现工作流
- 辅助工作流：无
- 是否需要回写：否

### 例子 2：把一个超大的详情页拆成多个区块组件
判断：
- 主任务类型：代码优化 / 重构
- 主工作流：前端实现工作流
- 辅助工作流：页面审查
- 是否需要回写：视情况
- 如果这种拆分模式后续能复用，再回写组件边界规范

### 例子 3：只有接口，想先推导一个新模块页面结构
判断：
- 主任务类型：原型 / 结构推导
- 主工作流：prototype + schema-to-ui
- 辅助工作流：page-design
- 是否需要回写：默认否

### 例子 4：某类详情页连续第三次都要补同样的状态区块
判断：
- 主任务类型：新页面 / 新模块开发
- 主工作流：前端实现工作流
- 辅助工作流：schema-to-ui
- 是否需要回写：是
- 回写目标：assets + docs，必要时进入 standards

---

## 结论
任务判断最容易犯的错有两个：
- 把所有任务都当成“实现任务”
- 把所有任务都强行拉进“回写治理”

正确做法是：
- 先定主工作流
- 再看是否叠加辅助流
- 最后谨慎判断是否需要回写

默认应偏保守：
**没有形成稳定规律，就不回写。**
