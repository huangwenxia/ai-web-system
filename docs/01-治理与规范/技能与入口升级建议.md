# 技能与入口升级建议

##目标
评审当前 `commands` 与 `skills` 的现状，给出从“提示词模板”升级到“稳定工作流入口”的补强方向。

## 当前现状判断
从现有文件看，你已经做对了几件关键事情：

1. 已经区分了 `standards`、`commands`、`skills`、`agents`、`docs`
2. 已经明确“规则正文不写在 Skill里”
3. 已经建立了按终端进行部署适配的思路
4. 已经有多条面向前端工作的入口模板

这说明你的体系不是从零开始，而是已经有了正确骨架。

---

## 当前 skills 的优势
以 `frontend-implementer-skill/SKILL.md` 为例，已有这些优点：

- 有角色设定
- 有必读标准路径
- 有适用任务
- 有输出顺序
- 有规则边界

这些内容说明它已经不是普通的一句话 prompt，而是有方法意识的入口模板。

---

## 当前 skills 的不足
如果希望被 Cursor、Cline、Codex、Claude Code 更稳定调用，还建议补齐以下结构：

###1.触发条件更明确
当前“适用任务”还不等于“何时必须调用、何时不该调用”。

建议补：
- `when_to_use`
- `when_not_to_use`

###2. 最小输入契约不够明确
当前缺少：
- 用户至少提供什么
- 缺哪些输入时必须追问

建议补：
- `required_inputs`

###3. 执行步骤还可以更细化
当前“输出顺序”比较清楚，但“分析 → 补全 → 校验 → 回写”的执行链还不够显式。

建议补：
- `workflow`

###4. 回写目标不够明确
目前只说“指出哪些结论应回写到标准库”，但还缺：
- 是写 `docs`还是 `standards`
- 是写 `examples`还是 `agents`

建议补：
- `writeback_targets`

###5. 协作关系还不清晰
当一个任务跨多个能力时，需要说明：
- 当前入口是否应转给其他 Skill
- 是否需要调用某个 Agent

建议补：
- `handoff`

---

## 推荐统一结构
建议今后的 `commands` 与 `skills` 尽可能对齐以下结构：

1.角色定位
2.适用场景
3. 不适用场景
4. 必需输入
5. 执行前先读取
6. 执行步骤
7. 输出格式
8. 回写目标
9. 协作 / 转交关系
10.规则边界

---

## 推荐优先升级的入口
考虑你的真实开发场景，建议先升级：

1. `frontend-implementer`
2. `page-analysis`
3. `schema-to-ui`
4. `ui-visual-review`
5. `page-design`

这是最接近日常页面开发闭环的一组入口。

---

## commands 与 skills 的治理建议
### commands
继续作为主维护层之一，负责表达通用入口逻辑。

### skills
继续作为终端可加载协议层，对 `commands` 做适配，不单独发散维护。

### 建议补一条治理原则
当新增某个入口时，应同时回答：

1. 它属于哪个闭环阶段？
2. 它是入口、执行、评审还是治理？
3. 它是否真的需要新增，而不是已有入口的扩展？

这样可以避免入口数量不断增长但职责重叠。

---

##结论
你现在的 Skill体系已经具备较强基础，不需要推翻重来。

真正需要做的是：

- 从“提示词组织”升级到“协议化入口”
- 从“单次任务输出”升级到“可回写、可协作、可治理的工作流”

只要按这个方向补齐结构，你的 Skill 就能更稳定地服务于 Cursor，也能更方便被像 Cline这样的智能体调用。
