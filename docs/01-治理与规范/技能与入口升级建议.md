# 技能与显式调用升级建议

## 目标

评审当前 `skills` 的现状，给出从“提示词模板”升级到“稳定任务协议”的补强方向。

## 当前现状判断

从现有文件看，已经做对了几件关键事：

1. 已经区分了 `standards`、`skills`、`agents`、`docs`
2. 已经明确“规则正文不写在 Skill 里”
3. 已经建立了按终端进行技能部署适配的思路
4. 已经形成多条面向前端工作的主 skill

## 当前 skills 的优势

以 `frontend-implementer-skill/SKILL.md` 为例，已经具备：

- 角色设定
- 必读标准路径
- 适用任务
- 输出顺序
- 规则边界

这说明它已经不是一句话 prompt，而是有方法意识的任务协议。

## 当前 skills 的补强方向

如果希望被 Codex、Claude Code、Cursor、Trae 更稳定调用，建议继续补齐：

### 1. 触发条件更明确

建议补：

- `when_to_use`
- `when_not_to_use`

### 2. 最小输入契约更明确

建议补：

- `required_inputs`

### 3. 执行步骤更显式

建议补：

- `workflow`

### 4. 回写目标更明确

建议补：

- `writeback_targets`

### 5. 协作关系更清楚

建议补：

- `handoff`

## 推荐统一结构

建议今后的 `skills` 尽可能对齐以下结构：

1. 角色定位
2. 适用场景
3. 不适用场景
4. 必需输入
5. 执行前先读取
6. 执行步骤
7. 输出格式
8. 回写目标
9. 协作 / 转交关系
10. 规则边界

## 推荐优先升级的技能

1. `existing-project-feature-skill`
2. `existing-project-fix-skill`
3. `page-review-skill`
4. `translate-terms-skill`
5. `frontend-implementer-skill`

## 治理建议

- Skill 继续作为主维护层之一，承担显式调用约定和执行协议
- 不再单独维护 `commands/` 适配层
- 新增 skill 时，必须同时回答：

1. 它属于哪个闭环阶段？
2. 它是执行、评审还是治理能力？
3. 它是否真的需要新增，而不是已有 skill 的扩展？

## 结论

现在的 Skill 体系已经具备较强基础，不需要推翻重来。

真正需要做的是：

- 从“提示词组织”升级到“协议化技能”
- 从“单次任务输出”升级到“可回写、可协作、可治理的工作流”
