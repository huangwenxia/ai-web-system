# Skill协议规范

## 目标
定义 `skills/*/SKILL.md` 的最小结构、职责边界与编写约束，让 Skill 在 Codex、Claude Code、Cursor 等入口里都能稳定复用，而不是变成一次性的提示词碎片。

## Skill 在体系中的位置
Skill 不是系统本体，它是“执行协议层”的一部分。

它的职责是：
- 告诉模型这个任务该按什么流程做
- 告诉模型优先参考哪些标准、模板和示例
- 约束输出格式、评审口径和边界检查点

它不负责：
- 代替标准库本身
- 存储任务历史
- 承担项目级配置中心功能
- 管理真实业务数据

## Skill 的双层结构

为了避免“按任务入口设计的工作流”和“按专业能力执行的细节”互相打架，Skill 应优先分成两层：

### 1. 任务型主 Skill

特点：

- 直接对应用户真实工作流入口
- 负责识别任务属于哪条主链路
- 负责组织闭环，而不是只输出一段分析
- 可以调用多个专业型子 Skill

适合承接的场景：

- 既有项目新功能开发
- 既有项目 bug 修复 / 代码优化
- 产品级审查与持续优化
- 翻译、术语统一与 i18n

### 2. 专业型子 Skill

特点：

- 直接对应某一段专业处理能力
- 可被多个任务型主 Skill 复用
- 负责把某个环节做专业、做稳定
- 不强行承担整个任务闭环

典型场景：

- 原型推导
- schema 到 UI 映射
- 页面设计
- 前端实现
- 页面结构审查
- UI 视觉审查
- UX 审查

### 3. 两层关系

- 任务型主 Skill 负责选主链路。
- 专业型子 Skill 负责把事情做专业。
- 不能因为引入任务型主 Skill，就直接删除仍然有复用价值的专业型子 Skill。

## 适用原则
一个 Skill 应该满足四个条件：
- 任务边界明确，只解决一类稳定问题
- 能引用已有标准，而不是重复描述整套体系
- 有固定输入、固定检查点和固定输出形态
- 可以在多个项目中重复使用

如果某段内容只适用于一次任务，应该放到任务模板或案例里，而不是做成 Skill。

如果要新增“任务维度”的 Skill，还必须额外满足：

- 它明确属于整个产品生产系统的一环
- 它能稳定提高效率、质量或交付一致性
- 它有固定输入、固定检查点和固定输出
- 现有工作流和专业 Skill 组合无法低成本覆盖

在满足这些条件之前，不新增新 Skill，也不为了“看起来更完整”补新文档。

```text
skills/
  agione-ui-skill/
    SKILL.md
  frontend-implementer-skill/
    SKILL.md
  page-review-skill/
    SKILL.md
```

如需补充引用材料，建议在 Skill 目录下继续加：

```text
skill-name/
  SKILL.md
  references/
  templates/
  examples/
```

## SKILL.md 最小结构
每个 Skill 建议至少包含以下部分：

### 1. 名称与用途
说明这个 Skill 解决什么问题。

示例：
- 用于根据接口结构推导页面骨架
- 用于审查页面视觉层级与状态完整性
- 用于把页面草稿落成 Vue 组件代码

### 2. 适用场景
明确什么时候该用，什么时候不该用。

### 3. 输入要求
列出模型执行前需要拿到的上下文，例如：
- 页面目标
- 接口字段
- 组件库约束
- 设计风格约束
- 目标技术栈

### 4. 执行步骤
把任务拆成稳定步骤，例如：
1. 识别任务类型
2. 梳理业务实体与状态
3. 匹配布局模式
4. 选择组件映射
5. 输出结果并补边界说明

### 5. 输出要求
明确产物应该长什么样，例如：
- 页面结构方案
- 组件清单
- 字段展示映射表
- Vue 代码
- 审查报告

### 6. 质量检查点
至少包含：
- 业务逻辑完整性
- 空态 / 异常态 / 权限态
- 组件复用优先
- 文案与状态术语统一
- 不越过既有前端规范

### 7. 引用资料
列出优先参考的标准文档、案例、模板路径。

## 编写约束
为了避免 Skill 失控，建议遵守以下约束：

- 不在 Skill 里堆大量项目背景知识
- 不把完整标准文档复制进 Skill
- 不写模糊指令，如“自行发挥”“自由设计”
- 不省略边界状态检查
- 不把某个项目的临时实现细节写成通用规则

Skill 应该更像“任务协议”，不是“长篇提示词”。

## Skill 与 commands 的关系
- `commands/` 更像用户触发入口
- `skills/` 更像模型执行协议

推荐做法：
- command 负责接收任务、组织上下文、触发 Skill
- Skill 负责规定执行步骤与输出质量

也就是说，command 偏入口，Skill 偏执行。

## Skill 与标准库的关系
Skill 不应直接替代标准库。

推荐关系是：
- 标准库定义原则
- 示例库提供案例
- Skill 组织调用方式
- Agent 或工作台负责执行与沉淀

这样才能避免每次升级标准时，要同时重写所有 Skill。

## 版本维护建议
每个 Skill 至少维护以下信息：
- 最近更新时间
- 适用技术栈
- 依赖的标准文档
- 已知限制

如果 Skill 变得越来越长，通常说明它承担了不属于自己的职责，应拆分。

## 结论
Skill 要解决的是“如何稳定执行一类任务”。

它应该准、稳、可复用，并持续引用标准库，而不是把所有知识都塞进自己内部。
