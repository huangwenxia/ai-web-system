# Agent适用边界清单

##目标
明确哪些事情值得做成 Agent，哪些事情更适合脚本，哪些事情必须保留人为决策，避免把整个系统过早做成一个职责混乱的“万能 AI 总控”。

## 判断原则
判断一个任务是否应该做成 Agent，可以看4 个维度：

1. 是否需要复杂判断
2. 是否需要跨规则归纳
3. 是否需要输出解释性结论
4. 是否不适合直接写死成脚本规则

如果一个任务只是“文件搬运、比对、扫描、校验”，通常优先脚本。
如果一个任务需要“评审、解释、抽象、归纳”，更适合 Agent。

---

## 非常适合建立 Agent 的任务
###1.组件入库评审 Agent
负责判断：
- 某组件是否值得进入知识库正式资产层
- 是否具备复用价值
- API 是否清晰稳定
- 是否只是页面私有拼装

###2. 知识库同步评审 Agent
负责判断：
- 某组件或页面是否适合从知识库同步到真实项目
- 风险点是什么
- 更适合放在项目哪里
- 是否需要再做一次工程化收敛

###3. 标准沉淀 Agent
负责从以下内容中提炼规则候选：
- 新组件
- 页面复盘
- Bug 修复
- UI 问题
- API设计经验

###4. UI 审查 Agent
负责审查：
-视觉层级
- 布局秩序
- 信息密度
- 空态、错误态、一致性问题

---

## 可以建立，但优先级次一级的 Agent
###5. 页面结构生成 Agent
适用于：
-只有接口，没有原型
-需要根据业务和字段快速生成页面结构方案

前提：
- 页面结构标准足够稳定
-你已经有足够多可复用范式

###6.依赖兼容性解释 Agent
适用于：
- 对脚本校验结果做解释
- 输出同步风险说明

注意：
- 真正的依赖扫描与校验本身仍建议脚本化

---

## 不建议优先建立 Agent 的任务
###1.纯文件同步 Agent
原因：
- 没有太多智能判断价值
- 脚本更稳定、更可控、更好审计

###2. 万能前端总控 Agent
原因：
- 容易把任务边界做乱
- 难以治理输出质量
- 后续维护成本高

###3. 全自动标准写入 Agent
原因：
- 标准库是体系源头
-需要强治理，不宜完全自动写入
- Agent适合提候选，不适合直接成为最终权威

---

## 脚本、Skill、Agent、人审 的推荐分工
### Skill
负责：
-执行协议
-读取标准
-组织执行顺序
- 固定输出格式

### Agent
负责：
- 专项评审
-复杂判断
-归纳解释
-规则候选提炼

### 脚本
负责：
- 扫描
- 比对
- 同步
-记录
- 校验

### 人审
负责：
- 最终取舍
- 标准确认
- 高价值资产入库决策
- 项目实际落地裁决

---

## 当前推荐的 Agent 建设顺序
1.组件入库评审 Agent
2. 知识库同步评审 Agent
3. 标准沉淀 Agent
4. UI 审查 Agent
5. 页面结构生成 Agent

如果资源有限，先做前3 个就足以形成闭环。

---

##结论
你的体系应该遵循：

- **标准本体是源头**
- **Command 是入口**
- **Skill 是执行协议**
- **Agent 是专项执行与评审**
- **脚本是稳定自动化基础设施**
- **人是最终治理者**

这能最大程度避免“所有事情都交给一个 AI解决”带来的失控问题。
