# Agent适用边界清单

## 目标

明确哪些任务值得做成 Agent，哪些更适合脚本，哪些必须保留人为决策。

## 判断原则

一个任务更适合 Agent，通常同时满足这些条件：

1. 需要复杂判断。
2. 需要跨规则归纳。
3. 输出需要解释性结论。
4. 不适合直接脚本化成固定流程。

如果任务只是文件搬运、扫描、比对、校验，通常优先脚本。

## 非常适合建立 Agent 的任务

### 1. 结构与方案评审 Agent

负责判断：

- 页面或组件方案是否清晰
- 信息层级是否合理
- 是否缺关键状态或交互路径

### 2. 项目落地风险评估 Agent

负责判断：

- 某段实现是否适合进入真实项目
- 风险点在哪里
- 是否还需要进一步工程化收敛

### 3. 标准沉淀 Agent

负责从以下内容中提炼规则候选：

- 页面复盘
- Bug 修复
- UI 问题
- API 设计经验

### 4. UI 审查 Agent

负责审查：

- 视觉层级
- 布局秩序
- 信息密度
- 空态、错误态和一致性问题

## 可以建立，但优先级次一级的 Agent

### 5. 页面结构生成 Agent

适用于：

- 只有接口，没有原型
- 需要根据业务和字段快速生成页面结构方案

前提：

- 页面结构标准足够稳定
- 已经有足够多可复用模式

### 6. 依赖兼容性解释 Agent

适用于：

- 对脚本校验结果做解释
- 输出落地风险说明

注意：真正的扫描和校验本身仍然更适合脚本。

## 不建议优先建立 Agent 的任务

### 1. 纯文件同步 Agent

原因：

- 智能判断价值低
- 脚本更稳定、更可控

### 2. 万能前端总控 Agent

原因：

- 容易让职责边界失控
- 输出质量难治理
- 后续维护成本高

### 3. 全自动标准写入 Agent

原因：

- 标准库是体系源头
- 需要强治理
- Agent 适合提候选，不适合直接成为最终权威

## 分工建议

### Skill

- 负责执行协议
- 组织执行顺序
- 固定输出格式

### Agent

- 负责专项审查
- 负责复杂判断
- 负责归纳解释

### 脚本

- 负责扫描
- 负责比对
- 负责校验
- 负责同步

### 人审

- 负责最终取舍
- 负责标准确认
- 负责真实项目落地裁决

## 当前推荐顺序

1. 结构与方案评审 Agent
2. 项目落地风险评估 Agent
3. 标准沉淀 Agent
4. UI 审查 Agent
5. 页面结构生成 Agent
