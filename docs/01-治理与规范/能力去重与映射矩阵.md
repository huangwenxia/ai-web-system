# 能力去重与映射矩阵

## 目标
明确 `standards / rules / commands / skills / agents / docs` 的职责边界，避免同一类能力重复写在多个层里。

## 结论
当前体系保留六层即可：

| 层 | 回答的问题 | 是否是规则权威 | 是否自动挂到 Cursor |
| --- | --- | --- | --- |
| `standards/` | 什么叫对 | 是 | 否 |
| `rules/` | 当前项目有哪些稳定约束 | 否 | 否 |
| `.cursor/rules/` | 这些项目约束怎样在 Cursor 中自动生效 | 否 | 是 |
| `commands/` | 用户如何触发一类任务 | 否 | 否 |
| `skills/` | 任务按什么协议执行 | 否 | 否 |
| `agents/` | 谁负责执行，多个 Agent 如何协作 | 否 | 否 |

## 去重原则
### 1. rule 只写约束
rule 可以写：
- 必须先确认上下文
- 必须复用现有组件和模式
- 必须覆盖边界状态
- 单点 bug 默认不回写规则

rule 不应该写：
- 详细 workflow
- handoff
- 使用哪个 skill
- 输出步骤清单

### 2. command 不重写 skill
command 只保留入口语义，不复制完整协议正文。

### 3. skill 不重写标准
skill 组织执行协议，但不复制 `standards/` 正文。

### 4. agent 不冒充执行协议
agent 只讲角色边界和协作职责，不承担完整任务步骤。

## 当前最容易重复的链路
### 既有项目前端开发
- rule：约束必须复用现有组件、先补齐边界、按已确认设计实现
- command：提供 `/frontend-implementer` 这类入口
- skill：定义实现任务的输入、流程、输出、handoff
- agent：定义“前端实现 Agent”负责什么

### bug 修复与代码优化
- rule：约束修改前必须确认调用方、复用范围和根因
- command：提供修复或实现入口
- skill：定义修复协议、检查点和输出格式
- agent：定义谁负责执行修复

### 页面结构推导 / 审查
- rule：不再承载这类 workflow
- command：提供显式入口
- skill：承载具体推导和审查协议
- agent：定义专项角色边界

## 维护顺序
1. 先改 `standards/`
2. 再改 `rules/`
3. 再同步 `.cursor/rules/`
4. 再改 `commands/`
5. 再改 `skills/`
6. 最后改 `agents/`

## 一句话判断
如果一份文件在回答“怎么做任务”，它大概率不该放在 rule 层。
