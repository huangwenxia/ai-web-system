# 能力去重与映射矩阵

## 目标
把 `rules / commands / skills / agents / docs / standards` 之间的关系讲清楚，避免后面继续出现：
- 同一份能力写四遍
- 入口、协议、角色、规则混在一起
- 不知道哪些文件还应该继续维护
- 不知道哪些内容已经被 Cursor Rule 覆盖

这份文档的重点不是删除文件，而是先定边界，再决定后续是否需要合并、降级或归档。

## 先给结论
当前体系不需要推翻，但要明确六层角色：

1. `standards/`
2. `docs/`
3. `.cursor/rules/`
4. `commands/`
5. `skills/`
6. `agents/`

它们的关系不是并列重复，而是：
- `standards/`：规则来源
- `docs/`：体系解释与治理说明
- `.cursor/rules/`：环境级默认约束与任务分流
- `commands/`：显式任务入口
- `skills/`：执行协议
- `agents/`：角色边界说明

## 各层职责矩阵

| 层 | 核心问题 | 当前是否应继续保留 | 是否是权威规则来源 | 是否会被 Cursor 自动挂载 |
| --- | --- | --- | --- | --- |
| `standards/` | 什么叫对 | 是 | 是 | 否 |
| `docs/` | 为什么这样设计、怎么治理 | 是 | 否 | 否 |
| `.cursor/rules/` | 在 Cursor 中默认怎么工作 | 是 | 否 | 是 |
| `commands/` | 用户怎样触发一类任务 | 是 | 否 | 否 |
| `skills/` | 模型怎样执行一类任务 | 是 | 否 | 否 |
| `agents/` | 谁负责什么、不负责什么 | 是 | 否 | 否 |

## 去重原则
### 1. 能力不要只看“内容像不像”，要看“职责是不是一样”
例如：
- `frontend-implementer` command
- `frontend-implementer` skill
- `前端实现Agent`
- `52-frontend-implementer-workflow.mdc`

它们都在谈“前端实现”，但职责并不相同：
- rule 负责默认挂载与环境分流
- command 负责触发入口
- skill 负责执行协议
- agent 负责角色边界

所以不能只因为它们主题相同，就简单删掉其中一层。

### 2. 真正应减少的是“无边界重复”
应该避免的是：
- command 和 skill 写成几乎一模一样的全文
- agent 文档去重新定义标准正文
- docs 去承担规则执行协议
- rule 去复制完整标准库内容

## 哪些内容已经被 Cursor Rule 覆盖
### 已被覆盖的部分
以下内容，现在已经有 Cursor 环境层承接：
- 工程默认行为
- 主工作流识别
- 任务分流
- Markdown 文档规范
- workbench 目录规则
- 回写治理触发条件

这些原来如果散落在多个文档里，现在可以把 `.cursor/rules` 视为“执行环境层的统一入口”。

### 仍未被覆盖的部分
以下内容仍然不能只靠 rule：
- command 的显式触发语义
- skill 的完整执行协议
- agent 的角色边界说明
- standards 的规则正文
- docs 的体系与治理解释

## 哪些文件后续可以降级为参考材料
当前还不建议删除，但可以逐步降低主维护优先级的，是：

### 1. 旧的 Cursor 适配探索文档
已进入：
- `docs/90-归档/cursor-适配探索/`

它们现在主要价值是：
- 保留探索过程
- 方便追溯为什么后来改成当前架构

不再作为主规则维护对象。

### 2. 某些与 command 高度重复的 skill 内容
现在先不删。

更稳妥的做法是：
- 继续保留
- 后续增强 skill 的“输入契约 / workflow / handoff / writeback_targets”
- 让它和 command 的差异变大

## 哪些文件必须继续作为主维护对象
优先级最高的主维护对象应该是：

### 第一优先级
- `standards/`
- `.cursor/rules/`
- `docs/01-治理与规范/任务类型判断矩阵.md`
- `docs/00-总览/Cursor规则分层与协同架构.md`

### 第二优先级
- `commands/`
- `skills/`

### 第三优先级
- `agents/`

原因：
- 规则来源、环境规则和任务分流先稳定，整个系统才不会散
- 入口和执行协议再逐步细化
- agent 角色边界相对稳定，更新频率应最低

## 当前最合理的维护顺序
以后建议按这个顺序维护：

1. `standards/`
2. `.cursor/rules/`
3. `docs/` 中的治理与架构文档
4. `commands/`
5. `skills/`
6. `agents/`

这样最符合“先规则、再环境、再入口、最后角色壳”的逻辑。

## 结论
当前体系不是“文件太多所以要删”，而是“边界还需要更明确”。

最重要的判断是：
- Rule 解决环境层问题
- Command 解决触发入口问题
- Skill 解决执行协议问题
- Agent 解决角色边界问题
- Docs 解决解释与治理问题
- Standards 解决规则权威问题

只要后续继续按这个矩阵维护，你的 `ai-web-system` 就不会越长越乱。
