# Git协作规范

## 目标
为 `ai-web-system` 建立一套轻量、稳定、适合个人持续积累的 Git 管理方式。

这份规范的重点不是团队审批流程，而是保证以下几件事：
- 标准库的演进可追踪
- 文档和脚本修改能分开管理
- 工作台代码变更不污染标准沉淀
- 提交历史便于回看和回滚

## 当前推荐策略
现阶段推荐使用：
- 单主干：`main`
- 小步提交
- 每次提交只做一类事情
- 先本地校验，再 push

对于你这个仓库，这比复杂分支模型更合适。

## 分支策略
### 默认分支
- `main` 作为长期主分支

### 什么时候新开分支
只有以下情况建议开分支：
- 做较大结构改造
- 做工作台功能开发
- 做一次可能反复调整的标准重构
- 做实验性方案，不确定是否保留

推荐命名：
- `feat/workbench-task-flow`
- `docs/standards-restructure`
- `chore/encoding-guard`
- `refactor/asset-manifest`

### 什么时候直接在 main 提交
以下情况可以直接在 `main`：
- 补充说明文档
- 小范围修正文案
- 修正脚本细节
- 修复编码和目录问题
- 增加案例与示例

## 提交粒度
这类仓库最怕“一个提交里什么都改”。

推荐按变更类型拆开：
- 标准文档一类提交
- 工作流文档一类提交
- 脚本工具一类提交
- Vue 工作台代码一类提交
- 资产样例一类提交

### 好的提交方式
- 只改 `docs/` 的架构说明，单独提交
- 只改 `scripts/` 的同步或校验逻辑，单独提交
- 只改 `apps/ai-front-workbench/` 的功能页面，单独提交

### 不推荐的提交方式
- 一次提交同时改标准、脚本、页面代码、示例
- 先大面积格式化，再混入真实逻辑修改
- 编码修复和业务改动混在一起

## 提交信息规范
推荐统一采用：

```text
<type>: <summary>
```

当前仓库建议的 `type`：
- `docs`：文档体系、说明、案例、路线图
- `feat`：新功能、新脚本、新页面能力
- `fix`：修复错误、修复乱码、修复配置
- `refactor`：重构结构，不改变核心用途
- `chore`：仓库维护、配置、初始化、清理
- `style`：纯格式调整，不改含义

### 示例
- `docs: 补充四层关系与闭环说明`
- `feat: 增加资产编码巡检脚本`
- `fix: 修复 docs 目录中文乱码`
- `refactor: 调整 workbench 页面路由结构`
- `chore: 初始化 ai-web-system 仓库`

## 提交前检查
每次提交前至少检查三件事：

### 1. 编码是否正常
```powershell
node scripts/verify-encoding.mjs .
```

### 2. 是否误提交不该入库的内容
```powershell
git status
```

重点看：
- `node_modules`
- 临时文件
- 日志文件
- 本地私有配置

### 2.5. 文档里是否残留本机绝对路径
如果本次改了 Markdown 文档，建议执行：

```powershell
rg -n "E:\\work\\ai-web-system" . -g "*.md"
```

同时参考：`docs/01-治理与规范/文档链接与路径规范.md`

### 3. 工作台代码是否至少能构建
如果本次改了 `apps/ai-front-workbench`，建议执行：

```powershell
cd apps/ai-front-workbench
pnpm build
```

## 推荐提交流程
日常建议使用下面这套：

```powershell
git status
node scripts/verify-encoding.mjs .
git add .
git commit -m "docs: 补充 Git 协作规范"
git push
```

如果只想提交部分内容，优先显式指定路径：

```powershell
git add docs README.md
git commit -m "docs: 更新体系说明入口"
```

## 目录对应的提交思路
### `standards/`
这里是标准本体。

建议：
- 修改时说明为什么改
- 如果是规则升级，最好同时补案例或引用来源
- 不要把一次任务里的临时结论直接写成标准

### `docs/`
这里是体系解释层。

建议：
- 一次提交围绕一个主题
- 先保证阅读顺序和关系清晰，再追求内容多
- 文档链接与命令示例遵守 `docs/01-治理与规范/文档链接与路径规范.md`

### `scripts/`
这里是执行工具层。

建议：
- 提交里写明脚本目的
- 如果改写文件行为，优先说明编码策略和副作用
- 尽量避免“顺手改很多脚本”

### `apps/ai-front-workbench/`
这里是产品化工作台层。

建议：
- 每次提交聚焦一个页面或一组相关功能
- UI 改动和数据结构改动尽量分开
- 提交前至少跑一次构建

### `assets/` 和 `examples/`
这里是沉淀层。

建议：
- 案例和模板新增时，说明用途
- 资产与 manifest 尽量一起提交

## 不建议提交的内容
- `node_modules/`
- 构建产物
- 本机日志
- 临时导出文件
- 与仓库无关的编辑器私有缓存

## 什么时候打标签
当前阶段不必频繁打 tag。

只有以下节点建议打标签：
- 第一版标准体系稳定
- 工作台达到可演示版本
- 资产治理脚本形成可复用组合

推荐示例：
- `v0.1.0`
- `v0.2.0-workbench`
- `v0.3.0-asset-flow`

## 适合你当前阶段的管理原则
你现在更适合“知识库式 Git 管理”，不是“企业发布式 Git 管理”。

核心原则是：
- 让历史可读
- 让问题可定位
- 让标准升级可回看
- 让实验和正式内容可区分

只要做到这些，这个仓库就已经具备长期演进基础。

## 结论
`ai-web-system` 的 Git 管理不需要复杂，但必须清晰。

优先保证：
- 单次提交单一主题
- 文档、脚本、代码分开提交
- 提交前做编码巡检
- 文档里不写本机绝对路径
- 主分支始终保持可读、可追踪
