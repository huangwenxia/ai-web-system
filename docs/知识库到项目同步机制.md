# 知识库到项目同步机制

##目标
定义 `ai-web-system` 与 `project-mamba`之间的同步原则，确保：

- 知识库独立于真实项目
- 知识库中的组件又能直接落回真实项目
- 同步过程可审、可追踪、可回滚
- 一份资产可以长期积累，而不是每次复制后失控

## 基本立场
###1. 知识库不是项目源码目录
`ai-web-system` 是你的前端知识库与组件资产库，不是 `project-mamba` 的子目录，也不是项目直接运行目录。

###2. 新产物先入知识库
AI 新生成的组件、页面、逻辑、模板、规范候选，优先落在知识库中，而不是直接写入真实项目。

###3. 知识库依赖真实项目生态
知识库中所有可落地组件，默认依赖 `project-mamba` 已存在的依赖与工程约束。

###4. 同步需要门槛
不是知识库里的所有内容都能同步回项目。只有通过校验和评审的资产，才能进入 `project-mamba`。

---

## 推荐同步流程
### Step1：产物生成
生成以下任一产物：
- 页面草稿
-组件草稿
- 数据映射方案
-视觉模式草稿
- 文档模板

产物先放知识库候选区。

### Step2：兼容性校验
必须先确认：
- 使用的依赖是否存在于 `project-mamba`
-代码风格是否兼容项目工程规范
-目标目录与模块归属是否明确
- 不存在知识库私有依赖泄漏

### Step3：成熟度评审
确认是否满足：
-复用价值成立
- API 足够稳定
- 命名足够通用
-视觉与交互质量达标
- 边界处理较完整

### Step4：同步决策
根据评审结果，分为：
- 不同步，仅保留知识库
-继续迭代后再同步
-允许同步到真实项目

### Step5：同步执行
同步时建议生成同步记录，包括：
- 来源路径
-目标路径
-适用项目
-依赖列表
- 同步时间
- 操作人 / 操作方式
-版本或批次标识

### Step6：回流沉淀
同步进入项目并使用后，要将反馈回流到知识库：
-组件优化建议
-失败经验
- 标准候选条目
- 新的 Skill / Agent 调整建议

---

## 哪些环节该用脚本，哪些环节该用 Agent
## 优先脚本化的部分
这些事情规则明确、可审计、重复度高，优先脚本比 Agent 更稳：

- 扫描依赖导入
- 检查目标目录
-生成同步 manifest
- 比对源文件与目标文件差异
-复制/更新文件
-记录同步日志

## 更适合 Agent 的部分
这些事情涉及判断、归纳、质量评审，更适合由 Agent 辅助：

-组件是否值得同步
-组件是否达到知识库正式资产标准
- 哪些问题应沉淀为标准
- 哪些内容其实只是页面私有逻辑，不应抽象

## 当前不建议的方案
- 不建议先做“万能同步 Agent”
- 不建议让 Agent直接黑盒把文件写进真实项目而不经过审查
- 不建议知识库自由引入项目之外的新依赖

---

## 推荐建立的同步分层
###1. 候选层
刚生成的页面/组件/模板，处于待审状态。

###2. 正式资产层
已经在知识库内部被认可，允许作为后续任务的复用来源。

###3. 项目同步层
已经确认可同步进 `project-mamba` 的资产。

###4. 项目落地层
真实项目中的最终代码。

这种分层可以避免“草稿直接污染项目”和“项目修改后知识库失联”两种常见问题。

---

## 建议的最小治理规则
### 必须遵守
1. 新产物先落知识库
2. 未校验兼容性，不允许同步
3. 未通过成熟度评审，不允许进入正式资产层
4. 同步必须有记录
5. 项目实战经验必须回流知识库

### 建议逐步建立
1. 同步 manifest机制
2.组件来源标记机制
3.资产版本号或批次号机制
4. 回滚策略
5.资产归属说明（页面私有 / 可复用 / 通用型）

---

##结论
你的目标不是让知识库变成第二个项目仓库，而是让它成为：

- 标准沉淀中心
- 可复用资产中心
- AI 工作流调用中心
- 项目经验回流中心

因此，“知识库 → 项目”的关系不应是随意复制，而应是**受控同步**。
