# 体系总览

## 这套系统到底是什么
`ai-web-system` 的目标，不是单纯存提示词，也不是单纯存组件。

它本质上是在做一套“本地优先的 AI 前端工作流系统”，用于把以下能力逐步沉淀下来：
- 业务梳理
- 页面原型推导
- 视觉与布局规则
- schema 到 UI 的映射
- 前端实现模板
- 页面与组件评审
- 资产复用与同步
- Cursor 环境下的规则编排

一句话概括：
它是在把“前端个人经验 + 组件资产 + AI 执行协议 + 项目级规则编排”整理成一个可持续复用的系统。

## 为什么需要它
如果只有零散提示词，会出现几个问题：
- 每次任务都要重新组织上下文
- 模型输出质量不稳定
- 好的页面结构和组件方案无法沉淀
- 审查标准只存在脑子里，无法复用
- 同一个问题会在不同项目反复重做
- 缺少项目级环境规则时，不同 AI 工具中的行为不稳定

所以要把能力拆成可积累的层，而不是继续靠临时对话推进。

## 体系的核心目标
这套系统主要服务三个目标：

1. 提升从接口到页面的产出速度
2. 提升页面结构、视觉和实现的一致性
3. 把一次任务中的有效结果沉淀成可复用资产和可复用规则

## 当前系统的组成
当前仓库可以理解成八个部分：

### 1. 标准层
定义“做事的规则”。

典型内容：
- 视觉标准
- 布局标准
- 数据映射标准
- 组件标准
- 文档标准

目录关注点：
- `standards/`
- `docs/`

### 2. 规则编排层
定义“在具体 AI 环境里，哪些约束应默认生效”。

典型内容：
- Cursor Project Rules
- User Rule 模板
- 项目级自动附加规则

目录关注点：
- `.cursor/`
- `docs/00-总览/Cursor规则分层与协同架构.md`

### 3. 入口层
定义“如何触发模型工作”。

典型内容：
- `commands/`
- `skills/`
- `agents/`

这一层的目标不是存知识，而是稳定调用知识。

### 4. 资产层
定义“沉淀什么可以复用”。

典型内容：
- 组件资产
- 页面模板
- 模式资产
- manifest 元数据
- 评审记录

目录关注点：
- `assets/`
- `examples/`

### 5. 工作台层
定义“如何把知识库变成可执行流程”。

典型内容：
- 本地工作台应用
- 项目任务编排界面
- 输入、输出、预览、决策记录

目录关注点：
- `apps/ai-front-workbench/`

### 6. 脚本层
定义“哪些动作可以工具化”。

典型内容：
- manifest 创建
- 资产校验
- 资产晋升
- 资产同步
- writeback 汇总

目录关注点：
- `scripts/`

### 7. 项目映射层
定义“知识库如何落到真实项目”。

典型内容：
- 目标项目依赖约束
- 组件适配记录
- 同步策略
- 预览接入方式

这一层目前主要通过文档、manifest 和脚本协同实现。

### 8. 治理层
定义“怎么保证沉淀不是垃圾堆”。

典型内容：
- 组件成熟度评审
- 页面复用价值评审
- 边界态检查
- 文档回写
- 标准回写
- 规则分层与定位约束

## 体系解决的主问题
从业务角度看，这套系统要解决三类问题：

### 第一类：从接口出发，快速得到合理页面
当没有原型图时，需要根据后端接口与业务语义，快速生成：
- 页面骨架
- 信息层级
- 数据展示方式
- 操作分区
- 状态补全

### 第二类：从已有设计出发，快速生成高质量代码
当已有页面设计被认可后，需要尽快落成符合组件库和项目规范的前端代码。

### 第三类：把一次次任务沉淀成复用能力
如果每次都只产出页面，不沉淀组件、规则和案例，长期效率仍会停在人工水平。

## 推荐理解方式
如果你是前端视角，不要一上来按“目录”理解，而要按“闭环”理解：

1. 需求 / 接口进入系统
2. 环境规则和项目规则先挂载
3. 系统根据标准推导页面方案
4. 方案落成代码或原型
5. 结果经过审查
6. 可复用部分沉淀成资产或规则
7. 资产再反哺下一次任务

先理解这个闭环，再回头看目录，很多东西就会自然对上。

## 当前第一版的定位
第一版不应该做成重后台产品。

更合理的定位是：
- 本地优先
- 文件优先
- 标准优先
- 规则分层优先
- 资产优先
- 工作流优先

也就是先把“能稳定做事”建起来，而不是先做复杂的数据库系统。

## 为什么先不重数据库
因为在当前阶段，真正稀缺的不是存储能力，而是：
- 规则是否清晰
- 目录是否合理
- 资产能否复用
- 输出是否稳定
- 评审是否能回写
- AI 工具中的默认行为是否可控

所以第一阶段优先用本地目录管理：
- 文档
- 模板
- 示例
- 组件资产
- 页面资产
- manifest
- Cursor rules

只有在开始需要复杂检索、聚合分析和任务历史追踪时，再引入 `better-sqlite3` 这类本地数据库。

## 后续可能的演进方向
当系统跑顺后，可以逐步往下扩：
- 增强工作台的任务编排
- 增强资产治理与检索
- 增强预览接入
- 增强项目同步能力
- 增强本地数据库索引
- 为其他领域补新的领域规则库

但这些都应该建立在第一版闭环可运行的前提上。

## 你现在最应该把它看成什么
最准确的理解方式是：

它不是“提示词仓库”。
它也不是“单一项目脚手架”。
它更像一个前端 AI 能力操作系统的雏形。

这个系统把：
- 规则来源
- Cursor 规则编排
- 入口
- 资产
- 评审
- 同步
- 预览

拼成一条可复用的前端交付链路。

## 结论
`ai-web-system` 的核心价值，不在某一个 Skill，也不在某一个命令，而在于它把“前端经验”转成了“可执行、可沉淀、可复用”的系统结构。

理解这个总目标，再去看每个目录和模块，技术实现就不会散。
