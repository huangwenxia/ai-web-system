# 前端开发闭环总流程

## 目标

把 `ai-web-system` 里的标准、规则、协议、示例和脚本串成一条可执行的前端开发闭环，确保每次任务都能稳定落地，并把值得保留的结论回写到正确位置。

## 推荐流程

0. 挂载环境规则
1. 接收任务
2. 梳理业务与输入
3. 产出页面或组件方案
4. 实现代码
5. 审查并修正
6. 回写标准、文档或示例
7. 接入真实项目

## 第零步：挂载环境规则

在 Cursor 或其它 AI 工具里，先让环境级规则生效：

- User Rule
- Cursor Project Rules
- 当前仓库的 Markdown 与回写治理规则

这一层负责提供默认工程行为，避免同一任务在不同工具里表现不一致。

## 第一步：接收任务

至少要先明确：

- 这是页面、组件、修复、审查还是文档任务
- 是否已有设计稿、参考页面或现成代码
- 最终产物是方案、代码、评审，还是规则沉淀

## 第二步：梳理业务与输入

把输入材料整理成可执行结构：

- 接口字段与实体关系
- 页面目标与用户操作
- 关键状态与异常状态
- 目标技术栈与项目约束

## 第三步：产出方案

如果没有成熟设计，先产出结构方案：

- 页面骨架
- 信息层级
- 区块划分
- 交互路径
- 状态补齐

## 第四步：实现代码

方案明确后再进入实现，重点是：

- 优先贴合真实项目约束
- 保持字段映射与业务语义一致
- 保证结构可维护、可拆分

## 第五步：审查并修正

至少检查这些维度：

- 信息层级是否清楚
- 视觉与交互是否稳定
- 状态是否完整
- 组件边界是否合理
- 文案和命名是否统一

## 第六步：回写标准、文档或示例

当任务中出现稳定结论时，按性质回写：

- 长期规则 -> `standards/`
- 流程解释与治理说明 -> `docs/`
- 典型案例 -> `examples/`

不要把一次任务里的临时判断直接写成长期规则。

## 第七步：接入真实项目

最终验证应回到真实项目或真实上下文中完成：

- 接入现有组件库与样式体系
- 验证边界态和业务流
- 记录落地约束与已确认结论

## 最小闭环

当前最值得优先跑通的是：

1. 明确任务与输入
2. 让规则先挂载
3. 产出方案
4. 落地代码
5. 完成审查
6. 回写稳定结论

只要这条链路稳定，仓库就能持续积累有效方法，而不是只堆一次性输出。
