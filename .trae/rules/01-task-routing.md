# 01 Task Routing

适用方式：默认加载

收到任务后，先做任务分流，再执行。

## 分流原则
1. 先选一个主工作流，不要一上来同时启动很多流。
2. 只有在主工作流不足以覆盖任务时，才叠加辅助工作流。
3. 默认不要把所有任务都拉进“回写规则”或“沉淀标准”流程。
4. 只有出现稳定规律时，才进入回写判断。

## 主工作流优先分类
优先判断任务属于哪一类：
- 纯 bug 修复
- 代码优化 / 重构
- 增量需求开发
- 新页面 / 新模块开发
- 原型 / 结构推导
- 审查类任务
- 文档 / 规则整理
- 资产治理 / 同步 / workbench 维护

## 默认路由
- 纯 bug 修复 -> 前端实现工作流
- 代码优化 / 重构 -> 前端实现工作流
- 增量需求开发 -> 前端实现工作流
- 新页面 / 新模块开发 -> 前端实现工作流；如果没有原型，再先走 prototype / schema-to-ui
- 原型 / 结构推导 -> prototype / schema-to-ui 工作流
- 审查类任务 -> page-analysis / ui-visual-review / ux-analysis 工作流
- 文档 / 规则整理 -> 文档工作流 / 规则整理工作流
- 资产治理 / 同步 / workbench 维护 -> 资产治理工作流 / workbench 工作流

## 辅助工作流判断
只有在以下情况再叠加辅助流：
- 修 bug 但背后暴露结构问题 -> 加页面审查流
- 新页面但只有接口没有原型 -> 加 prototype / schema-to-ui
- 代码优化涉及视觉或交互质量 -> 加 UI / UX 审查流
- 审查后要直接改代码 -> 再加前端实现流

## 回写判断
默认先假设：不需要回写。

只有满足以下至少一条，才考虑回写：
- 同类问题重复出现
- 结论可跨页面 / 跨模块复用
- 能明显减少下一次同类任务判断成本
- 已形成稳定审查口径
- 已形成稳定组件 / 页面 / 规则模式

## 明确不回写的常见情况
- 一次性项目特例
- 单点 bug 修复
- 小范围样式修正
- 一次性兼容写法
- 复用性尚未验证的临时实现

## 输出建议
在复杂任务中，先显式给出：
- 主任务类型
- 主工作流
- 辅助工作流
- 是否需要回写
