# agione-req-refine Skill

## 用途

`brief.md` 定稿后、进入 `/agione-prototype-prep` 前的需求细化阶段引导。

通过四个阶段的结构化采访与协作，将业务简报深化为可供研发拆解、可供原型生成的完整方案文档：

- **Phase 1** — solution.md（跨功能主方案）
- **Phase 2** — flow.md（主流程与状态流转）
- **Phase 3** — functions/ 骨架（功能模块识别 + 文件生成）
- **Phase 4** — batch-align.md（待拍板问题汇总）

## 触发方式

```
/agione-req-refine [REQ 目录路径]
```

示例：
```
/agione-req-refine knowledge-base/02-projects/agione-platform/requirements/REQ-2026-001-account-foundation
```

---

## 执行规则（AI 必须遵守）

1. **先问后写**：任何文档产出必须在该阶段采访完成、用户确认后才能开始，禁止边问边生成。
2. **优先给选项 + 纵排**：凡有有限答案的问题，必须给 2-4 个选项让用户选；**每个选项独立成行**（不要 `A. xxx  B. yyy  C. zzz` 横排在同一行——窄终端会自动换行导致编号和内容错位）。不要让用户凭空组织语言。
3. **一轮最多 3 个问题**：不允许在一轮里堆砌超过 3 个问题。
4. **不自行脑补**：信息不足必须停下来问清楚，不允许自行推断业务规则。
5. **只写业务层**：字段名、接口规范、SQL 不属于本阶段范畴，禁止出现在产出文档中。**业务层状态流转**（如 Active → Archived、PENDING → APPROVED）属于本阶段，但**技术层状态机实现细节**（如数据库枚举值、状态码映射）不属于。
6. **不修改上游文档**：brief.md 和 acceptance-checklist.md 只读，不允许修改。
7. **增量写入**：每个阶段完成后立即写文件，用户可随时中断，已完成部分不丢失。

## Phase 1 — solution.md 采访与起草

### 1.1 如果 solution.md 已存在

切换为确认模式：

```
## solution.md 已存在（版本：{版本号}）

当前内容摘要：
- 核心对象：{列出}
- 核心业务规则：{前 3 条}
- 功能方案章节：{列出}
- 待确认问题：{数量} 条

- A. 内容无误，跳过 Phase 1，进入 Phase 2
- B. 需要补充/修改某些章节（请说明）
- C. 重新采访，完全重写
```

### 1.2 solution.md 采访（5 个维度）

每轮选取最相关的 1-3 个问题，覆盖以下 5 个维度。每个维度不超过 2 轮问答。

**维度 1：核心对象与角色关系**

> 本期涉及哪些核心业务对象（如 Project、Key、Transaction、Quota 等）？
> 这些对象之间的主要关系是什么？
> 哪些角色可以操作哪些对象？

⚠️ **Phase 1 / Phase 2 边界**：本维度只讨论对象是什么、对象间关系是什么、谁能操作谁。**不讨论流程步骤**（"先做A再做B"这类描述留给 Phase 2 的 flow.md）。如果用户在此阶段描述了流程，记录下来但不写入 solution.md，留到 Phase 2 处理。

示例提问格式：
```
## Phase 1 · 第 1 轮

Q1 — 核心业务对象
从 brief.md 中识别到以下对象，请确认：
- A. 全部正确：[列出识别到的对象]
- B. 需要增加（请说明）
- C. 需要删减（请说明）

Q2 — 对象归属关系
[对象A] 和 [对象B] 之间的关系是？
- A. [对象B] 属于 [对象A]（一对多）
- B. 两者独立，通过 [关联字段] 关联
- C. 其他（请描述）
```

**维度 2：核心业务规则**

> 有哪些跨功能的约束或计算逻辑？（例如：额度扣减顺序、审批触发条件）
> 优先级或互斥关系是什么？

**维度 3：方案边界**

> 本期明确做哪些、不做哪些？（基于 brief.md 再次确认，看是否有变化）
> 有没有「看似相关但这次不做」的能力点？

**维度 4：跨功能权限原则**

> 多角色/多主体场景下的隔离约束是什么？
> 哪些操作需要特殊权限？哪些数据对哪些角色不可见？

**维度 5：依赖与风险**

> 这个需求依赖哪些上游系统或数据？
> 最可能出问题的地方在哪里？
> 有没有需要提前协调的下游影响？

### 1.3 信息确认

5 个维度采访完成后，展示摘要：

```
📋 solution.md 采访完成，确认关键信息：

- 核心对象：{列表}
- 主要角色关系：{描述}
- 核心业务规则：{前 3 条}
- 本期做：{列表}
- 本期不做：{列表}
- 权限约束：{描述}
- 主要依赖/风险：{列表}
- 待确认问题：{列表}

确认无误回复「可以」，有调整直接说。
```

### 1.4 起草 solution.md

用户确认后，严格按照 `templates/solution-template.md` 结构生成，规则：
- 只写跨功能业务层，不写字段/接口/状态机细节
- 所有内容来自采访结果，不允许编造
- 信息不足处标注 `⚠️ 待补充：{说明}`
- 末尾「待确认问题」章节必须保留（即使为空）
- **§8.1 代码地图对口必填**：基于 `00-overview/code-map.md` 第 1 / 10 节，把"功能方案"映射到具体仓库 / 模块。规则：
  - "主要落点"表至少列出每个本期能力对应的后端仓库 + 前端 app
  - 如果识别出跨仓库桥（典型例：`metis-cbdp` ↔ `metis-wanmore` 的 `CbdpRechargeController`、`metis-hashrate` 的 `Wm*Controller`），必须在"跨仓库桥"小表里列出
  - 拿不准的落点写 `⚠️ 待研发 Owner 在 functions/§9.1 进一步细化`，不要硬猜 Controller 名字

写入路径：`[REQ路径]/solution.md`

写入后输出：
```

→ 进入 Phase 2（flow.md）？
- A. 是，继续
- B. 先暂停，下次继续
```

## Phase 2 — flow.md 采访与起草

## Phase 3 — functions/ 功能模块骨架

### 3.1 功能模块识别

从 `solution.md` 和 `flow.md` 中提取功能模块，呈现建议清单。

**拆分粒度原则：**
- 一个 function 应对应**一个独立可验收的功能点**
- 粒度参考：一个 function ≈ 1-3 个页面 + 对应的业务规则
- 太粗的信号：单个 function 包含超过 5 个页面，或涉及 3 种以上不同角色的独立操作
- 太细的信号：两个 function 共享完全相同的对象和流程，只是页面不同（应合并）

```
## Phase 3 · 功能模块识别

基于 solution.md 和 flow.md，识别到以下功能模块，建议按此拆分为独立的功能说明书：

| # | 功能 ID | 功能名 | 主要内容 | 预计页面数 | 来源 |
|---|---------|--------|---------|:---------:|------|
| 1 | F001 | [功能名] | [核心能力描述] | ~N | solution §5.1 |
| 2 | F002 | [功能名] | [核心能力描述] | ~N | solution §5.2 |
| 3 | F003 | [功能名] | [核心能力描述] | ~N | flow §4 |
| ... | | | | | |

- A. 全部正确，按此生成骨架
- B. 需要增加（请说明）
- C. 需要删减或合并（请说明编号）
- D. 需要重命名或调整（请说明）
```

### 3.2 生成功能说明书完整内容

用户确认模块列表后，**为每个功能生成完整的功能说明书**（全部 §1-§12），不留空章节。

- 文件路径：`[REQ路径]/functions/F{NNN}-{slug}.md`
- 严格按照 `templates/function-spec-template.md` 结构
- **全部 12 个章节都必须填写**，内容来源优先级：

| 章节 | 内容来源 | 填写规则 |
|------|---------|---------|
| §1 功能概述 | brief.md + solution.md | 一句话描述、使用频率、角色、对应 AC |
| §2 前置条件 | solution.md + flow.md | 提取操作的前置条件 |
| §3 主流程 | flow.md Happy Path | 具体到页面 + 动作 + 系统响应 |
| §4 字段定义 | solution.md 对象模型 + tech-solution.md（如有） | 推导字段名、类型、校验规则；信息不足处标注 `⚠️ 待确认` |
| §5 异常场景 | flow.md 异常流程 + 业务逻辑推导 | 编号 E01-ENN，含触发条件、系统行为、提示文案 |
| §6 状态机 | flow.md 状态流转 | 文本流程图 + 状态转移表（当前状态/动作/下一状态/谁能操作） |
| §7 权限控制 | solution.md 权限规则 | 角色 × 操作矩阵 |
| §8 埋点/审计 | flow.md 审计建议 + 业务逻辑推导 | 关键事件、触发时机、参数 |
| §9 边界约束 | solution.md 约束 + 业务逻辑推导 | 数量上限、限流、过期、多租户隔离 |
| §9.1 代码地图对口 | solution.md §8.1 + `00-overview/code-map.md` | 后端仓库 / Maven 模块 / 主 Controller / 主 Service / 主 Entity / Feign 端口 / 跨仓库桥 / 前端 app / i18n / 权限码。拿不准的字段写 `⚠️ 待 Tech Lead 拍板`，不要硬猜路径 |
| §10 UI 状态要求 | 通用规则 + 功能特性 | 空/加载/错误/权限不足态 |
| §11 待 PM 拍板 | solution.md 待确认问题 + AI 发现的歧义 | 业务背景必须解释清楚，不能只写引用 |
| §12 关联文档 | 自动填入 | brief/solution/flow 的对应章节引用 |

**信息不足时的处理规则：**
- 如果某个字段/规则在上游文档中未定义但可以从业务逻辑合理推导 → 写入内容，标注 `💡 AI 推导`
- 如果无法推导 → 标注 `⚠️ 待确认：{说明为什么需要补充}`
- 禁止编造业务规则（如费率、阈值等具体数值），必须标注待确认

### 3.3 功能说明书确认（批量 or 逐个）

全部功能说明书写入文件后，**必须经用户确认**才能进入 Phase 4。

```
- B. **逐个深度确认**：每个功能单独走"摘要 → 修改循环"

建议：功能数 ≤ 3 → B；功能数 ≥ 5 → A；中间数量按个人偏好。
```

```
- 回复 "全部确认" → 直接进 Phase 4
- 回复 "F003 / F005 要改" → 这两个进逐个深度审查（其余视为确认）
- 回复 "全要逐个看" → 切换为模式 B
```

#### 模式 B — 逐个深度确认（推荐 ≤3 功能 或 模式 A 中标记要修改的功能）

## Phase 4 — batch-align.md 汇总

### 4.1 汇总逻辑

扫描所有 `functions/F*.md` 的 `§11 待 PM 拍板汇总` 章节，汇总所有待拍板问题，按优先级分类：

| 分类 | 判断条件 |
|------|---------|
| 必决（阻塞开发） | §11 中「是否阻塞开发」标注 ✅ |
| 重要（影响多功能） | 问题出现在 2 个以上功能中 |
| 一般（单功能内，不阻塞） | 单功能、不阻塞 |
| 建议研发自决 | 与业务规则无关、纯实现选择 |
