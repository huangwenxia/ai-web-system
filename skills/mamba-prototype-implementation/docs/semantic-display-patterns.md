# 语义展示模式库

本文件沉淀前端实现中可复用的“界面语义识别 → 展示方式选择 → 是否抽组件”的判断口径。

## 轻量结构化规格碎片（lightweight structured spec fragments）

### 定义
当同一字段的 value 由多个短碎片组成，且这些碎片共同服务于快速扫读，而不是承担分类、筛选、点击或语义状态时，应将其识别为“轻量结构化规格碎片”。

典型例子：
- `L20X × 8`
- `160核`
- `1800G`

这些值共同组成字段 `规格` 的 value，而不是三个独立字段，也不是三枚业务标签。

### 判断特征
1. **同一字段的拆分值**
   - 它们都属于某一个字段的 value，不是独立字段。
2. **说明性碎片，不是分类性标签**
   - 不是 tag / badge / category。
   - 不是“可筛选、可点击、可归类”的对象。
3. **服务于扫读**
   - 目标是让用户更快读懂规格组成，不是突出某种业务语义。
4. **应该服从字段节奏**
   - 它们应该长得像“被拆开的 value”，不是像一组独立的业务标签。

### 展示原则
- 优先把它视为字段 value 的局部表达，而不是业务标签系统。
- 视觉上应弱于主状态、弱于主操作，服从所在字段行的节奏。
- 高度、边框、圆角、字重、间距应优先贴合当前字段区的 key/value 语言，而不是独立发展成一套 tag 语言。
- 如果页面已有明确原型，优先贴原型的节奏；若原型颜色 token 与项目 UI 规范冲突，则以项目 token 体系兼容落地。

### 实现建议
- 单页单处出现时，可保留为局部字段碎片实现。
- 组合 Element Plus 原生组件时，不要因为存在 `el-tag` 就先把它误判成 tag 语义。
- 只有当它在多个页面/模块中重复出现，并且语义稳定一致时，才考虑抽象成项目级组件。

## 抽项目级组件铁律：语义模式复用阈值

当项目中多个地方反复出现同一类“语义展示模式”时，不要继续在各页面各写一套局部实现；满足以下条件后，应正式抽成项目级组件：

1. 命中同一语义模式至少 2 处以上（例如多个页面都存在“轻量结构化规格碎片”）。
2. 这些出现点的语义一致，不是偶然长得像。
3. 视觉目标一致：都应服从同一字段区或同一信息层级。
4. 抽象后能减少页面内重复判断、重复 Tailwind 片段或重复局部样式。

### 组件命名导向
- 应按语义命名，而不是按视觉命名。
- 例如：
  - `SpecFragments`
  - `FieldValueFragments`
  - `StructuredValuePieces`
- 避免命名成：
  - `TagList`
  - `BadgeRow`
  - `ChipGroup`
  除非它本质上真的是标签/徽章语义。

### 不该抽的情况
- 仅单页面一次性特例。
- 外观相似但语义不同。
- 抽象后只会把页面内局部判断转移到一个更模糊的通用组件里。
