# 细节与连续性交接：跨系统改造方法

适用于既有系统的局部精修和操作体验升级，不是新页面设计规范，也不是全站动画清单。
功能、文案、业务结构和结果保持不变；只分析时不修改产品代码，实施及浏览器工具仍受本次授权约束。

## 1. 从用户任务定位“生硬”

先明确目标用户、当前任务、操作频率、点击前后应保持的对象。沿用户真实动作分析，不按组件目录逐个补效果。

| 可见/可复现现象 | 优先检查的断点 | 候选机制 |
|---|---|---|
| 操作像散落字段、补图标后拥挤或换行 | 视觉单元、间距来源、容器容量 | 单一间距责任、图文比例和操作列容量协调 |
| 点击后不知道是否生效 | 输入到即时反馈断开 | 原生 active/focus/loading，必要时实体按钮轻按压 |
| 当前项突然从一处跳到另一处 | 同一选择缺少状态连续性 | 共享选中背景/指示器迁移，文字与命中区不动 |
| 收起后所有内容猛跳、展开像分段加速 | 几何让位和尺寸续接断开 | 实测高度、保留当前位置，必要时同向速度接续 |
| 新结果闪一下再开始动画 | 首帧和真实数据提交顺序错误 | 提交前准备，布局后同帧释放并显现 |
| 转圈→空白→数据，或父区展开完子表才动 | 等待与结果被串成多轮演出 | 原生等待/骨架与结果交接重叠，单一高度责任 |
| 每次输入、后台刷新都像首次入场 | 触发范围过宽 | 区分显式选择、查询变化、同范围刷新和静默更新 |
| 点击完成后“飞走”，但不知道去了哪里 | 结果空间归属断开 | 优先就地结果；确有可见目标时才做来源→结果交接 |

以上是诊断入口，不是已证实缺陷。源码可支持机制判断，截图只能支持静态现象，动态手感须观察真实交互才能确认。
没有动画但操作明确、稳定，也可能是正确方案。

## 2. 静态基础：让间距和图标承担明确职责

### 间距不是一组魔法数字

检查顺序：视觉单元 → 组内/跨组关系 → 对齐基准 → 尺寸来源 → 容器容量。

- 同一按钮组只保留一个组间距来源，例如 flex gap；排查组件自带相邻 margin、图标 margin 与文字 margin 的叠加。只在拥有该组的作用域修正，不全局清零。
- 区分图文内部间距、按钮之间的间距、操作组与业务内容的间距，不把三者统一成同一个值。
- 补图标或改字重后重新评估列宽、长文案、权限下最多同时出现的操作；`nowrap` 不能凭空提供可用宽度。不能通过隐藏操作、删文字或缩小点击区偷过验收。
- 两栏起点/底边不齐时，追踪共同父级的布局责任和实际剩余画布，不先加负 margin 或额外卡片。调整业务布局超出授权时只提出方案。
- 采用项目现有密度与 token；案例中的像素只说明当时的解决方式，不升级为跨项目规范。

### 图标是一部分操作语言

- 先判断图标是对象类别、操作、展开提示还是业务状态；角色不清不补。数值容器或只读字段即使用了 Button 也不因此成为操作。
- 同一任务内同义操作优先同一语义图标；沿用项目图标库和按需导入，不为精致强制全站换库。
- 图标外框与实际图形黑区不同；尺寸、笔触、字重和文字基线一起判断。不得把固定描边、全体变细变浅、换字体当成普适清晰度方案。
- 图标可见尺寸不等于命中区；维持键盘焦点与可访问名称，禁用/请求中/危险操作语义不能被装饰覆盖。
- 不默认“所有按钮都需要图标”。高密度行操作尤其要评估冗余、宽度和主次，不把局部统一需求扩成全局规则。

涉及字体来源、光学对齐或交付判断时，按 `../page-review-skill/docs/ui-craft-gates.md` 的条件与证据边界检查。

## 3. 用“交接契约”代替动画清单

每个实际要改的断点，用最短记录回答下面问题；简单 hover 不必建立额外状态机或配置平台。

| 契约项 | 要确定的内容 |
|---|---|
| 对象与不变量 | 哪个对象在变化？哪些文字、数据、入口、焦点、滚动或挂载策略必须保留？ |
| 触发与排除 | 用户选择、真实请求完成还是本地增删？输入、校验、轮询等哪些变化不触发？ |
| 空间责任 | 谁负责指示器、内容显现、尺寸让位？父子哪些层明确不再重复运动？ |
| 时序交接 | 何时取旧画面、提交新 DOM、量终态、安装首帧、解除骨架、显示结果？ |
| 中断与归属 | 连点、反向、旧回调、隐藏、卸载怎样处理？请求结果归属由谁管理？ |
| 降级与恢复 | 减弱动效、能力不足、目标不可见时如何保持完整静态反馈，并还原临时样式/属性？ |

### 一次点击的时序

1. **即时确认**：沿用原生按压/焦点/选中反馈；不等动画播完才执行动作，不为动画另加防抖或锁住下一次点击。
2. **真实等待**：绑定真实请求，不用定时器伪造加载；等待、失败、空结果分开。骨架不写进业务数组、统计、选择或导出。
3. **空间交接**：需要旧几何时先读当前可见画面，再取消旧补间；提交后量新几何，在绘制前安装反向位移/高度首帧，避免先露终态再拉回。
4. **结果落定**：用已成功的业务事实触发结果反馈，不延迟业务 Promise 等演出。原生关闭、焦点恢复、异常传播继续由原机制负责。

这是职责顺序，不是每段必须串行等待。高度让位与子内容显现可同帧进行；不同输入类型也不需要同一种动画。

## 4. 可迁移的机制及取舍

### A. 选中背景连续迁移

适用：同容器内互斥选项、当前树节点、已有导航/Tab。

- 动背景/指示器，不移动标签和点击目标。首次定位原地出现，后续相邻选择再迁移。
- hover、当前选中、键盘 focus 是不同状态；hover 离开后，当前项仍须明确。hover 到当前项避免两层背景叠色。
- 滚动、筛选、折叠、缩放或 Teleport 变换后重新定位/撤回旧坐标；目标不可见时回退原生状态，不追赶旧位置。
- 原组件已有合适指示器就复用；不增加第二根滑条。共享运动背景不是给普通字段新增装饰胶囊的理由。

### B. 展开、筛选与条件字段的几何让位

适用：原本就存在的收放、条件显示、详情展开；不因效果新增折叠功能。

- 读真实高度，不猜 `max-height: 999px`。有必要退出动画时，目标态与呈现态可短暂分离，但不能改变值、校验、请求条件和长期挂载策略。
- 即将隐藏内容先退出交互；焦点在其中时交还仍可见的相关控件。透明不等于不可点击或不可被 Tab 聚焦。
- 反向从当前高度立即响应；同向慢内容多次到达，若重启动画产生分段加速，再考虑速度/剩余时间续接，而不是一律引入弹簧系统。
- 多层展开由当前层负责高度，父层随文档流；字段位置按所属分组计算，避免把上游让位算进每个子项再动一次。
- 临时裁切不能裁掉操作或让下拉浮层失效；最终交还原自然布局/高度策略。

### C. 真实数据、骨架与结果显现

适用：已有远程列表、树、详情内容；等待和结果是不同表面。

- 首次加载可用轻量骨架；已有内容刷新是否保留旧值或覆盖骨架，依任务与项目模式决定，不统一清空旧数据。
- 骨架按真实列、已有几何和固定列组织；占位数量是展示策略，不伪装为真实数据量或进度。
- 接口完成后先让原组件提交数据/列宽，移除骨架并交接父区高度，再同帧开启结果显现；不要“遮罩退完→整块淡入→逐行出现”层层串行。
- 查询/页码改变可有短促波次，同范围刷新更轻，静默更新通常不重播；只作用于可见内容并封顶总时长，不按全数据量线性排队。
- 位移不能扩大底部滚动范围；空态、隐藏 Tab、固定列、短列表分别检查。不把加 `overflow: hidden` 裁掉内容当成修复。
- 动效版本号只约束装饰回调；响应竞态须由原请求层处理，不悄悄增加缓存、预取、排序或返回对象转换。

### D. 本地增删与位置补间

适用：已有配置项、文件列表、地域/可用区、无分页本地表格。

- 优先稳定业务 ID；没有 ID 时仅在对象身份确实稳定的局部用 WeakMap/对象身份。不得把动画 key 写入 payload，也不能用数组下标把删除后的另一项当作原对象。
- 已有项只补间位置，新项局部显现；同长度编辑通常就地交接，不重播整表。
- 已有 TransitionGroup/上传组件增删过渡就调它的节奏，不再包一层。最后一项原本立即卸载时，不克隆交互表单来拖延业务删除。
- FLIP 是读取旧/新几何并反向补间的方法，不等于必须使用某个框架组件或引入新库。

### E. 成功来源到真实结果

适用：低频且结果去向明确的提交/创建任务；通常属于可选增强，不是每次成功都要“飞入”。

- 优先现有就地状态/原生成功通知。只有真实可见的结果承接点、明确的方向关系和授权，才考虑更强的收束/吸入表现。
- 先建立本次真实结果，后量实际落点；多任务逐次关联，不能飞向硬编码角落、另一张通知或无关导航。
- 视觉副本只作短生命周期装饰，须不可交互、不可读屏、清除重复 ID/自动聚焦；不重复挂载业务组件、不存储/上传表单内容。
- 原弹层入退场只能有一个表现责任。视觉取消或失败保留同一真实结果，不能补发通知、伪造成功或改变 Promise/关闭语义。
- 目标移位、离屏、关闭、偏好变化或卸载时停止装饰；无稳定落点直接降级。强形变实现成本高，普通系统先复用简洁反馈，不复制案例分片数量。

## 5. 快速迁移与验证

### 迁移顺序

先选一条代表性任务链，按收益定位最小公共落点：

1. 修正已证实的图文/间距冲突和当前态辨识。
2. 连接最高频的选择→等待→结果、展开→让位路径。
3. 核查单链状态与清理逻辑，再扩到同类调用点；真实交互效果默认由用户人工确认，成功收束等强表现按业务需要单独决定。

CSS 能解决的状态不建 composable；需要真实几何/中断管理才用局部指令或 hook。
同应用多处复用才考虑适配组件；跨应用共享层须有独立证据、授权与回归，不能为了“统一灵动”顺带升级。
不默认增加全局 MotionProvider、全站动画扫描器或新的动画依赖。

### 最小验证矩阵

以下是按风险选择的检查与人工查看提示，不是每次实施都要自动执行的测试矩阵；不为覆盖清单新增专项脚本。涉及对应逻辑时检查源码，真实交互默认由用户人工确认：

- 正常→等待→成功 / 失败 / 空结果；快返回与慢返回。
- 连续同向、快速反向、旧完成回调晚到；隐藏/卸载/重新进入。
- 已有选中、焦点、输入、校验、权限、插槽和公开 ref 接口不变。
- 长文字、最多操作、短/长列表、固定列、窄画布和滚动边界。
- 减弱动效初始开启与中途开启；暗色/弹层/目标失效。
- Timer、帧任务、Observer、监听器、Animation、inert 和临时样式恢复。

日常修改优先 diff、引用、语法与 UTF-8 核查；有具体逻辑风险时复用已有局部测试，不新建 SFC 加载器、mock 运行环境或 `test-*.mjs`。需要保留新的回归测试时先说明风险与成本并取得确认。历史案例中的测试数量与脚本不是当前任务的最低要求。
代码写完、耗时检查前先告知可以手动查看；非必要检查卡住或明显耗时则停止并说明，不反复补脚本或扩大检查。浏览器自动化、截图、性能测量及构建不由本方法自动授权。
人工体验检查也要明确“待检查”，不能把清单当作已完成证据。

### 复盘怎么写

保留“症状 → 可核查实现/历史 → 连续性断点 → 机制 → 取舍/不变量 → 反例 → 验证边界”。
区分已提交、工作区未提交、候选建议；历史文档不等于当前事实，历史测试结果不等于本轮重跑。
最终分别说明：信息架构是否因本次需要变化、视觉/动态是否已有验收证据、存在何种已证实的必须修正项。
