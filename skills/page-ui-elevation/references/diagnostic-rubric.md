# 体验升级建议与实施输出规范

输出服务于用户当前问题，不固定评分、候选数量或完整报告。探索建议与执行修改分开。

## 共同边界

- 既有功能、文字、业务信息结构、操作入口和结果保持不变；涉及变化时单独说明并等待明确授权。
- 可以探索既有控件的视觉表现和动画机制；不把功能保护解释为组件形态冻结。
- 明确区分截图可见现象、已核实行为和待确认候选；未观察到的动态行为不作缺陷断言。
- 基础可用性、实际缺陷和可选体验提升分别表达。某种动画缺失本身不是缺陷，不抬高为交付阻塞。
- 用户举例、提供参考或表示喜欢，不等于要求采用、授权代码修改或授权浏览器自动化。

## 用户询问升级借鉴时

先回答值得探索的方向，而不是先列一长串基础检查或工程限制。
建议围绕以下内容组织，可用短段落或表格，不要求机械套标题：

| 内容 | 应回答的问题 |
|---|---|
| 当前对象 | 哪个已有区域或控件，服务什么任务？ |
| 参考组件或机制 | 能联想到什么？没有合适具名组件时直接说明机制，不编造出处。 |
| 契合点 | 为什么适合这里，而不是仅因为演示好看？ |
| 适配方式 | 借什么、不借什么，何时触发，哪些内容和行为保持不变？ |
| 取舍与建议 | 改善什么，有什么代价，推荐程度如何？ |

示例：历史列表可探索菜单式背景连续迁移，只让高亮层在条目间衔接，标题和点击区域保持静止。
若快速扫过时产生拖尾追赶，或 hover 混淆当前项，就不采用该表现。
这只是机制映射示例，不是所有侧栏的默认方案。

- 不强制找具名组件、凑多套方案，也不只重复 Press、Focus、Reveal、Tooltip。
- 不因某组件来自营销展示就直接排除，先拆解可迁移机制；无收益时可以明确建议保持原样。
- 只问建议时不强制输出代码。用户需要更具体说明时，可提供状态顺序或适配示意，不擅自编辑文件。
- 默认不打分。用户要求评分时，仅评有证据的维度；截图不足以评估动态手感、帧率或交互完整性。

## 用户明确授权实施时

先确认目标组件、现有能力和授权范围，再实施选定方向；不能把探索中的其他候选顺带落地。

实施说明按实际需要覆盖：

- 改动位置、采用的机制与项目现有组件/动效能力的复用。
- 保持不变的文字、入口、业务规则和操作结果。
- 减弱动效、键盘焦点、快速重复操作与相关布局边界。
- 实际运行的验证、未验证部分及最小人工检查建议。

代码与参数必须根据真实实现提供，不能凭截图声称可直接替换。
未运行浏览器或性能测量时，不声称已完成视觉验收或达到某个帧率；仍遵循用户与项目的工具授权和验证限制。
