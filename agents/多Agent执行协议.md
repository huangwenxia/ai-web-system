# 多 Agent 执行协议

## 目标
把 `agents/` 从“只有角色说明”补成“可执行的协作协议层”。

这份协议不假装仓库已经内置某个真实产品的多 Agent 引擎，而是定义：
- 主 Agent 什么时候值得拆任务
- 子 Agent 应该拿到什么输入
- 结果如何回收、冲突如何处理
- 哪些任务不该硬拆成多 Agent

## 核心原则
- 先选一个主工作流，再决定是否拆子 Agent。
- 主 Agent 负责总目标、任务切分、依赖顺序、结果汇总和最终交付。
- 子 Agent 只负责清晰、稳定、边界明确的子任务，不自行扩张职责。
- 多 Agent 不是默认动作，只有能显著降低上下文混乱或并行加速时才使用。
- 所有 Agent 都以 `standards/` 为规则来源，以 `rules/` 或 `.cursor/rules/` 为环境约束来源。

## 角色
### 主 Agent
负责：
- 识别主任务类型
- 选择主工作流
- 判断是否需要拆子任务
- 给每个子 Agent 分配明确输入、输出和边界
- 回收结果并做冲突仲裁
- 给出统一结论与回写判断

不负责：
- 把每个局部子问题都亲自重做一遍
- 在没有必要时滥拆多个子 Agent

### 子 Agent
负责：
- 在限定边界内完成指定子任务
- 明确引用的标准、假设和风险
- 在需要时把问题升级回主 Agent

不负责：
- 擅自更改总目标
- 覆盖其他子 Agent 的结果
- 把一次性结论写成长期规则

## 何时拆分
满足至少两条才建议拆子 Agent：
- 主任务可以分成两个以上相对独立的子问题
- 子问题之间的输入输出边界清晰
- 子问题可以并行推进，不会互相频繁阻塞
- 子问题适合由不同专业角色处理
- 主 Agent 自己继续全做会明显增加上下文负担

常见可拆场景：
- 一个任务同时包含 `schema-to-ui`、实现、审查
- 同时要产出代码、文档和规则回写建议
- 同一个页面存在结构问题、视觉问题和实现问题，需要并行诊断

## 不拆的情况
以下情况默认不要拆：
- 单点 bug 修复
- 小范围样式调整
- 高度耦合、必须连续推理的实现任务
- 输入不足、主问题还没澄清
- 只是为了看起来像“多 Agent”而拆

## 标准执行流程
1. 主 Agent 读取 `rules/` 或 `.cursor/rules/`，完成任务分流。
2. 主 Agent 判断主工作流、辅助工作流、是否需要回写。
3. 主 Agent 评估是否值得拆子 Agent。
4. 如需拆分，先定义子任务清单，再给每个子 Agent 分配责任。
5. 子 Agent 各自执行并返回结果、依据、风险和待确认项。
6. 主 Agent 做结果汇总、冲突处理和最终输出。
7. 主 Agent 判断是否需要回写到 `standards/`、`docs/`、`examples/`、`assets/`、`rules/`。

## 子任务分配模板
每个子 Agent 至少应被告知：
- 子任务名称
- 目标结果
- 输入范围
- 可读参考
- 不可越界的事项
- 输出格式
- 是否允许提出回写候选

推荐模板：

```md
子任务：<名称>
负责 Agent：<agent 名称>
目标：<要完成什么>
输入：<可用输入>
必读：<标准 / 规则 / skill / command>
边界：<不负责什么>
输出：<期望产物>
```

## 推荐分工模式
### 模式 A：结构 -> 实现
- 主 Agent：识别任务，确定主链路
- `Schema映射Agent`：先做结构映射
- `前端实现Agent`：基于已确认结构落代码

适用：
- 接口到页面
- 新页面 / 新模块开发

### 模式 B：实现 -> 审查
- 主 Agent：先安排实现
- `前端实现Agent`：完成代码或修复
- `UI审查Agent` 或审查类 Skill：做结构 / 视觉 / UX 复核

适用：
- 重构后复审
- 页面修复后补质量检查

### 模式 C：实现 + 文档
- 主 Agent：统筹范围
- `前端实现Agent`：实现或修复
- `组件文档Agent`：补 usage / spec / 边界说明

适用：
- 组件抽象完成后补文档
- 组件复用前做文档沉淀

## 结果回收规则
- 子 Agent 输出必须显式区分：事实、推断、建议。
- 如果两个子 Agent 结论冲突，由主 Agent 做最终裁决。
- 如果冲突来自规则缺失，应标记为候选回写项，而不是让子 Agent 各说各话。
- 最终交付只保留主 Agent 汇总后的统一结论。

## 与 command / skill / rule 的边界
- `rules/` 或 `.cursor/rules/`：默认环境约束、任务分流与目录级规则
- `commands/`：显式入口
- `skills/`：单个任务流的执行协议
- `agents/`：多角色分工与交接协议

## 当前约束
- 当前仓库已经具备“多 Agent 协议层”，但还不等于任何具体产品已经原生支持多 Agent。
- 如果目标工具没有原生 subagent 能力，就由主 Agent 按这份协议手动执行分工和回收。
- 如果目标工具支持 subagents，再把本协议映射为具体产品配置。
